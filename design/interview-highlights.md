## 项目亮点

### 1. 不是只做链上调用，而是强调链上结果消费

项目重点不在“怎么发一笔交易”，而在：

- 如何读取 `receipt（交易回执）`
- 如何解析 `event log（事件日志）`
- 如何把链上结果转换成后端可用的业务数据

### 2. 不是只做充值或提现单点流程，而是强调完整资金链路

项目设计同时覆盖：

- 充值监听
- 确认数处理
- 提现申请
- 审核与广播
- 状态跟踪
- 账本与流水

### 3. 不是只维护余额字段，而是显式引入账本思维

项目设计里明确区分：

- 可用余额
- 冻结余额
- 充值记录
- 提现单
- 资金流水

### 4. 强调真实后端工程关心的问题

包括但不限于：

- 幂等
- 断点续跑
- 确认数
- 链重组
- 签名边界
- 对账与补偿

## 高频面试题与标准表达

## 1. 为什么充值不能一监听到就入账

因为后端监听到一笔链上转账，只能说明“当前观察到了一次候选入金事件”，并不代表它已经稳定到可以做内部账务确认。后端还需要确认：

- 交易是否真正执行成功
- 事件日志是否正确
- 确认数是否足够
- 是否存在 `reorg（链重组）` 风险

更稳妥的做法是先生成一条待确认充值记录，等确认数达标后再做正式入账。

## 2. 为什么 ERC-20 充值监听通常依赖 Transfer 事件

因为 ERC-20 转账通常是调用 token 合约方法，而不是直接做原生币转账。交易里的 `value` 往往可能是 0，真正的收款地址和金额更可靠地体现在 `Transfer event（转账事件）` 中。因此后端通常会通过 `receipt + event log` 来识别充值，而不是只看交易表面字段。

## 3. 为什么提现申请后要先冻结余额

因为提现不是瞬时完成的，中间还会经过审核、签名、广播和状态跟踪。如果不先冻结余额，同一笔资金在处理期间可能被重复占用，最终造成账务不一致。所以提现申请后通常要先把可用余额转为冻结余额，等链上最终成功后再正式扣减，失败则回退。

## 4. 为什么拿到 txHash 还不能说提现成功

因为 `txHash（交易哈希）` 只表示交易已经被构造并广播出去，并不代表链上已经成功执行。后面还可能出现：

- 交易未被打包
- 交易执行失败
- 确认数不足
- `nonce（交易序号）` 冲突
- 替换交易或卡单

所以真正的成功判断应该以 `receipt.status` 和确认数为准。

## 5. 钱包后端为什么一定要有内部账本

因为链上余额只能反映某个地址当前持有多少资产，但平台业务真正需要的是更细粒度的资金状态，包括：

- 可用余额
- 冻结余额
- 待确认充值
- 提现处理中金额

如果没有内部账本，平台就很难支持冻结、流水、审计、补偿和对账，也无法高效提供余额查询和业务状态管理。

## 6. 钱包后端最核心的能力是什么

不是单纯收钱和打钱，而是把链上变化稳定地同步成平台内部账务，并通过幂等、确认数、签名边界、对账和补偿机制保证账实一致。

## 7. 提现系统最重要的风险点有哪些

提现系统最核心的风险通常有：

- 重复打款
- nonce 管理混乱
- 签名能力暴露
- 广播成功但执行失败
- 状态机混乱导致账务不一致

因此提现系统往往会重点建设：

- 冻结机制
- 审核流
- 签名边界隔离
- 状态跟踪
- 审计日志

## 8. 这类项目和传统 Java 后端经验的连接点在哪里

连接点非常强，尤其体现在：

- 支付与清结算
- 账务与资金流水
- MQ 异步处理
- 幂等与补偿
- 风控与审核
- 可观测性与稳定性建设

Web3 后端的特殊性在于“外部事件源变成了区块链”，但很多核心工程问题和传统资金系统非常接近。
