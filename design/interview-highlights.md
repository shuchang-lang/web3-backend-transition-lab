## 为什么这个项目有面试价值

### 1. 它不是只会调用链上接口

项目重点不在“怎么发一笔交易”，而在：

- 怎么消费 `receipt`
- 怎么解析 `event log`
- 怎么把链上变化翻译成平台内部账务
- 怎么处理链上和账本之间的不一致

### 2. 它不是只做 happy path

项目里明确补了这些治理主题：

- `confirmations`
- `reorg`
- `compensation`
- `nonce reuse`
- `serialized broadcast`
- `reconcile`
- `task observability`

这些点恰恰是资金后端比普通 demo 更值钱的部分。

### 3. 它和传统 Java 资金后端经验连接很强

你完全可以把这个项目讲成“区块链是新的外部事件源，但后端治理问题和传统资金系统高度相似”：

- 幂等
- 状态机
- 冻结 / 解冻
- 补偿
- 对账
- 审计
- 可观测性

## 建议重点强调的 6 个亮点

### 1. 充值不是直接入账，而是“候选记录 -> 确认数达标 -> 正式入账”

这个点能体现你理解区块链结果的不确定性，而不是把链上事件当成传统数据库事务。

### 2. 提现不是直接打款，而是“申请冻结 -> 审核 -> 广播 -> 回执同步 -> 最终扣减 / 回退”

这个点能体现你对资金安全边界和状态机设计的理解。

### 3. `nonce` 不是简单自增，而是要考虑复用、冲突和串行保护

这是典型的 Web3 后端特有问题，也很适合在面试里讲出区别度。

### 4. `reorg` 风险识别和补偿机制让项目更像真实资金后端

这是很多简历项目里没有的部分，但对交易所 / 钱包后端非常关键。

### 5. 自动对账把“账实一致”从接口能力升级成了任务能力

这个点特别适合把 Java 后端里的对账经验迁移到 Web3 场景中。

### 6. 审计日志和指标概览让任务具备了最小可观测性

这说明你不只是做业务流，还开始关心稳定性和运维表达。

## 面试官可能追问的点

### 1. 为什么 ERC-20 充值监听更依赖 `Transfer event`

因为 token 转账的核心信息通常不在原生交易 `value` 字段里，而在合约执行后的 `event log` 中。  
所以钱包后端更可靠的做法是读 `receipt + event log`，而不是只看交易表面字段。

### 2. 为什么不能一监听到转账就直接给用户加钱

因为那只是候选入金事件，还不代表链上状态已经稳定。  
后端还需要处理：

- 交易是否成功
- 日志是否正确
- 确认数是否足够
- 是否存在 `reorg` 风险

### 3. 为什么提现申请后要先冻结余额

因为提现存在审核、广播和状态跟踪过程。  
如果不先冻结，资金在处理中就可能被重复占用，最终造成账务不一致。

### 4. 为什么有了 `txHash` 还不能算提现成功

因为 `txHash` 只表示交易已经广播，不表示链上已经成功执行。  
真正的成功通常要看：

- `receipt.status`
- 是否被打包
- 是否发生替换交易
- 确认数是否足够

### 5. 为什么钱包后端一定要有内部账本

因为链上余额只能反映地址当前持仓，不能直接表达业务态资金状态。  
平台真正需要的是：

- 可用余额
- 冻结余额
- 待确认充值
- 提现处理中金额
- 资金流水

### 6. 这个项目最难的地方是什么

可以优先讲这几类：

- 链上状态和平台账务的翻译关系
- 提现状态机和 `nonce` 治理
- `reorg` 风险下的补偿与冲正
- 自动对账和任务可观测性

## 高频问题标准表达

## 1. 这个项目最核心的价值是什么

不是单纯打通链上调用，而是把“链上结果消费、平台内部账务、异常治理和任务治理”串成了一条完整后端链路。

## 2. 这个项目最能体现你哪些 Java 后端能力

- 资金账本设计
- 幂等控制
- 状态机流转
- 补偿与冲正
- 对账思维
- 任务治理与可观测性

## 3. 你觉得 Web3 后端和传统资金后端最大的区别是什么

最大的区别在于外部事件源变成了区块链，结果天然带有确认延迟、`reorg`、`nonce`、广播失败等链上不确定性。  
但一旦把这些不确定性翻译成后端模型，很多治理问题和传统支付、清结算系统其实是相通的。

## 4. 为什么这个项目适合你转到钱包后端或交易所后端

因为它覆盖的不是零散概念，而是资金后端最核心的几件事：

- 入金
- 出金
- 账本
- 补偿
- 对账
- 稳定性治理

这些能力和钱包后端、交易所资金后端岗位是直接相关的。
