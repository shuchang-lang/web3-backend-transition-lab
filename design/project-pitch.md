# Project Pitch

## 用途

这份文档专门用于 Day29 的项目表达收口，目标不是补技术细节，而是把“这个项目该怎么介绍、怎么演示、怎么应对追问”整理成可直接复用的话术。

---

## 30 秒版本

> 我做了一个面向 EVM 生态的钱包后端实践项目，技术栈是 Java 17、Spring Boot、MyBatis-Plus、MySQL 和 web3j。项目不是单纯调链上接口，而是把充值监听、提现执行、内部账本、异常补偿、自动对账和任务可观测性串成了一条完整的资金后端主线。

---

## 60-90 秒版本

> 这个项目主要是为了把我原来在 Java 后端里关于账务、幂等、状态机、补偿和对账的经验，迁移到 Web3 钱包后端场景里。  
> 我先做了 ERC-20 充值扫描、确认数推进和正式入账，再做提现申请、冻结、审核、广播和回执同步。然后继续补了真实资金后端更关心的治理能力，比如 `reorg` 风险识别、异常充值补偿、`nonce` 串行保护、任务失败分层、自动对账，以及任务审计日志和指标概览。  
> 所以这个项目更像一个小型资金后端，而不是几个孤立的 Web3 demo。

---

## 3 分钟版本

### 1. 项目背景

我本身是做 Java 后端的，目标是尽快切到 `钱包后端 / 交易所后端 / 链上数据后端`。  
所以这个项目从一开始就不是往纯合约开发方向做，而是围绕“资金后端工程”来设计。

### 2. 技术路线

技术栈上我用的是：

- `Java 17`
- `Spring Boot`
- `MyBatis-Plus`
- `MySQL`
- `web3j`

之所以这样选，是因为我的目标不是做前端钱包，而是做后端系统，所以重点放在：

- 链上数据消费
- 账本与流水
- 状态流转
- 补偿与对账

### 3. 主链路

充值这边：

- 扫 ERC-20 `Transfer event`
- 识别候选充值
- 推进确认数
- 达标后正式入账

提现这边：

- 先申请并冻结余额
- 审核通过后待广播
- 预留或复用 `nonce`
- 广播上链
- 再同步回执，最后成功扣减或失败回退

### 4. 治理能力

在 happy path 之外，我重点补了这些能力：

- `reorg` 风险识别
- 异常充值补偿与冲正
- 提现广播失败分层与自动重试
- 单 JVM 串行广播保护
- 自动对账与结果落库
- 审计日志和指标概览

### 5. 项目价值

我觉得这个项目最有价值的地方，是把区块链的不确定性翻译成了 Java 后端熟悉的工程问题，比如：

- 幂等
- 状态机
- 冻结 / 解冻
- 补偿
- 对账
- 审计
- 可观测性

所以它既能展示 Web3 理解，也能展示后端治理能力。

## 面试时建议主动讲的主线

### 主线一：资金状态主线

`充值 -> 提现 -> 账本 -> 流水`

### 主线二：异常治理主线

`reorg -> 补偿 -> 超时巡检 -> 失败分层`

### 主线三：稳定性主线

`幂等 -> nonce 治理 -> 串行广播 -> 对账 -> 可观测性`

如果你主动按这三条线讲，面试官更容易觉得项目结构完整。
