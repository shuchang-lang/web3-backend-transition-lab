# Wallet Backend Module Design

## 设计目标

这个项目不是为了模拟“一个能调链上接口的 demo”，而是为了尽量用最小代码量表达真实资金后端会关心的模块边界。

到 Day29 为止，模块设计重点体现：

- 链上事件消费
- 内部账务处理
- 提现状态流转
- `reorg` 风险治理
- 自动对账
- 任务审计与可观测性

---

## 模块划分

### 1. 地址管理模块

职责：

- 给用户分配充值地址
- 维护用户、链、币种与地址的映射
- 支撑充值地址查询

对应价值：

- 解决“平台如何知道这笔入金属于谁”
- 是充值链路的入口锚点

### 2. 区块扫描与进度模块

职责：

- 保存扫描断点
- 支持断点续跑
- 控制区块扫描窗口

对应价值：

- 解决“扫描任务重启后怎么继续”
- 让链上消费具备最小批处理能力

### 3. 日志解析与候选充值识别模块

职责：

- 过滤目标合约
- 读取 ERC-20 `Transfer event`
- 识别平台充值地址
- 生成候选充值记录

对应价值：

- 解决“如何从链上事件里抽出可入库的业务数据”
- 避免只看交易表面字段导致识别不准

### 4. 充值确认与正式入账模块

职责：

- 刷新确认数
- 达到阈值后推进正式入账
- 更新余额主表
- 写资金流水

对应价值：

- 解决“候选充值什么时候可以变成平台内部资金”
- 把链上不确定性翻译成平台账务确定性

### 5. 提现申请与审核模块

职责：

- 创建提现单
- 冻结余额
- 审核通过 / 拒绝
- 支撑解冻回退

对应价值：

- 解决“提现处理中资金如何避免被重复占用”
- 把风控审核和账务冻结串起来

### 6. 提现广播与回执同步模块

职责：

- 预留或复用 `nonce`
- 广播链上交易
- 同步交易回执
- 成功扣减或失败回退

对应价值：

- 解决“从平台订单到链上执行结果”的映射问题
- 把 `txHash`、回执、订单状态和账务状态统一起来

### 7. 账本与流水模块

职责：

- 管理可用余额与冻结余额
- 对所有资金变化落流水
- 承载充值入账、提现冻结、解冻、成功扣减、冲正等动作

对应价值：

- 解决“不能只靠链上余额支撑平台资金状态”
- 支撑审计、补偿、对账和余额查询

### 8. 风险治理与补偿模块

职责：

- 识别 `reorg` 风险
- 对异常且已入账的充值做冲正
- 对异常提现做超时巡检和人工处理分层

对应价值：

- 解决 happy path 之外的真实异常场景
- 让项目更接近交易所 / 钱包后端的资金治理逻辑

### 9. 对账模块

职责：

- 校验余额主表、流水、充值、提现之间是否一致
- 生成自动对账批次
- 沉淀历史结果快照

对应价值：

- 解决“系统有没有长期偏差、漏记、错记”
- 把对账从一次性查询能力升级成任务能力

### 10. 任务治理与可观测性模块

职责：

- 统一任务名称和批次号
- 记录任务审计日志
- 汇总任务指标概览
- 查询最近任务执行情况

对应价值：

- 解决“任务是否执行、执行结果如何、失败原因是什么”
- 为后续监控、告警和排障提供基础

## 当前最核心的主线

如果只看这个项目最重要的一条主线，可以概括成：

`链上事件 -> 候选记录 -> 平台账务 -> 异常治理 -> 自动对账 -> 任务可观测性`

这个表达很适合 GitHub 和面试，因为它能让别人快速理解项目不是零散接口，而是一条资金后端主线。

## 当前模块之间的依赖关系

### 充值方向

1. 地址管理模块提供地址归属
2. 区块扫描模块推进断点
3. 日志解析模块识别候选充值
4. 充值确认模块推进正式入账
5. 账本模块更新余额和流水
6. 风险治理模块处理 `reorg`
7. 对账模块定期检查账实一致
8. 可观测性模块记录任务执行轨迹

### 提现方向

1. 提现申请模块先冻结余额
2. 审核模块决定是否进入待广播
3. 广播模块负责链上发送与 `nonce` 治理
4. 回执同步模块推进最终状态
5. 账本模块做成功扣减或失败回退
6. 超时巡检模块治理异常订单
7. 对账模块检查提现与账本口径是否一致
8. 可观测性模块记录任务运行情况

## 当前设计原则

### 1. 链上状态与平台账务分层

链上交易、日志、回执只是事实来源，平台真正可用的是经过确认、落库和状态机翻译之后的内部账务。

### 2. 所有资金变化都要落流水

余额主表只负责表达当前状态，真正能说明“为什么变成这样”的是流水。

### 3. 异常治理不依赖人工兜底

项目优先做：

- 自动重试
- 失败分层
- 补偿
- 对账

人工处理是边界，而不是默认方案。

### 4. 任务必须可观测

只做任务入口不够，还要回答：

- 有没有执行
- 最近一次什么时候执行
- 是成功、跳过还是失败
- 本轮关键计数是多少

---

## 适合面试时怎么讲

你可以把模块设计总结成下面这句话：

> 我把项目拆成地址管理、区块扫描、充值识别、提现执行、内部账本、异常治理、自动对账和任务可观测性几个模块，核心思想是先把链上事件翻译成平台内部账务，再用补偿、对账和审计日志保证账实一致和任务可追踪。
