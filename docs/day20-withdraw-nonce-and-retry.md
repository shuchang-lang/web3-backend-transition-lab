# Day 20 - 提现 nonce 管理与广播重试第一版

今天进入 `Day 20`。

如果 `Day19` 解决的是：

`审核通过的提现订单，怎么真正广播到链上，并根据回执决定扣减还是回退`

那么 `Day20` 要继续往前补的，就是提现执行里一个非常典型、也非常容易踩坑的 Web3 后端问题：

`nonce 怎么管理，广播失败后订单怎么安全重试`

这一步的重要性非常高，因为很多“看起来能跑”的提现系统，真正一上链就会卡在这里。

---

## 一、为什么 Day20 要优先补 nonce 管理

对于做过多年 Java 后端的人来说，第一次接触 `nonce` 时很容易把它理解成：

`交易流水号`

这个理解不算错，但还不够。

在 EVM 链上，`nonce` 更像是：

`某个地址发出的交易顺序号`

它直接决定两件事：

1. 同一个热钱包地址发出的交易必须按 `nonce` 顺序执行
2. 如果同一个地址用了重复 nonce，后发交易可能会覆盖前一笔，或者被节点拒绝

所以对钱包后端、交易所后端、托管后端来说，`nonce` 不是一个可有可无的字段，而是：

`链上出金执行顺序控制的核心键`

Day19 虽然已经具备广播与回执跟踪能力，但当时还没有把这个问题补完整。

如果还停留在 Day19 的状态，真实环境里很容易碰到几类问题：

1. 一轮广播失败后，下轮重试重新分配了新 nonce
2. 不同订单在失败重试过程中抢同一个热钱包的 nonce
3. 订单已经预留过 nonce，但后面广播时又被改掉
4. 排查链上问题时，后台看不到订单本来想用哪个 nonce

所以 Day20 的目标不是“多加一个字段”，而是：

`让提现广播从能跑，进一步升级成更像真实执行系统的最小版本`

---

## 二、Day20 的核心目标是什么

今天要解决的事情，可以概括成 4 点：

1. 广播前先为提现订单预留 `nonce`
2. 本地订单记录要保存这次预留的 `nonce`
3. 如果广播失败，订单不能直接失败，而是继续留在 `PENDING_BROADCAST`
4. 下次重试时，优先复用已经预留过的 `nonce`

翻译成更工程化的话，就是：

`提现广播任务要从“一次性尝试”升级成“带最小重试语义的执行任务”`

这一步对 Web3 后端非常关键，因为链上广播失败并不总意味着业务失败。

很多时候失败原因可能只是：

- 节点瞬时异常
- RPC 超时
- 网络抖动
- 上一笔交易还没被节点接受完成
- 节点返回了临时性错误

如果系统一遇到异常就把提现直接判成 `FAILED`，业务层会非常难受，也不符合真实执行系统的行为。

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经把下面几块补起来了。

### 1. Web3Gateway 明确暴露“建议 nonce”能力

`Web3Gateway` 新增了：

- `getSuggestedWithdrawNonce()`

这一步的意义在于：

`业务层不再自己猜 nonce，而是显式向链网关索取当前建议起点`

这样做有两个好处：

1. nonce 来源统一
2. 以后如果从 web3j 切到托管钱包、签名服务、MPC 服务，业务层接口不用大改

在当前 `web3j` 实现里，建议 nonce 来自：

`eth_getTransactionCount(address, pending)`

这里用的是 `pending` 视角，而不是 `latest`。

原因很简单：

`pending` 能把“已经进入节点内存池、但还没正式上链”的交易也统计进去

这对于连续广播多笔提现尤其重要。

### 2. 广播接口改为显式传入 nonce

Day19 版本的广播逻辑，更多还是：

`网关内部自己拿 nonce，然后直接广播`

Day20 把它改成：

`应用层先决定这笔提现该用哪个 nonce，再交给网关广播`

也就是说，`broadcastErc20Withdraw(...)` 现在增加了 `nonce` 参数。

这一步非常关键，因为它意味着：

`nonce 分配权开始回到提现执行服务，而不是散落在底层 SDK 里`

一旦这层权责立住，后面做下面这些能力都会更顺：

- nonce 锁
- 顺序广播
- 失败重试
- 替换交易
- 人工排障

### 3. 提现订单开始保存预留 nonce

`withdraw_order` 对应的领域对象 `WithdrawOrder` 增加了：

- `reserveNonce(Long nonce)`

并且订单里本来就已经有：

- `nonce`

Day20 让这个字段不再只是“广播成功后顺手记录一下”，而是变成：

`广播执行前就要先落库的关键状态`

这是一个很重要的变化。

因为从现在开始，订单已经不仅记录：

- 提现申请参数
- 审核结果
- 交易哈希

还开始记录：

- 这笔订单原本打算占用哪个链上顺序号

这对排障、补偿和重试都很有帮助。

### 4. 提现执行服务新增“解析可用 nonce”逻辑

`WithdrawExecutionAppService` 现在新增了两段非常关键的逻辑：

- `resolveNextAvailableNonce()`
- `reserveNonceIfNecessary(...)`

这两个方法组合起来，完成的是最小版本的 nonce 分配。

#### `resolveNextAvailableNonce()` 做了什么

它会同时参考两类信息：

1. 节点返回的建议 pending nonce
2. 本地订单里已经预留或已广播的最大 nonce

然后取更安全的那个起点。

为什么要这样做？

因为真实执行环境里，经常会出现这种情况：

1. 某笔订单已经在本地预留了 nonce
2. 但这一轮广播失败了
3. 节点那边暂时还没看到这笔交易

如果下一轮只相信节点返回的 pending nonce，就可能把这个 nonce 又分配给别的订单。

Day20 现在做的，就是尽量避免这种最常见的顺序错乱问题。

#### `reserveNonceIfNecessary(...)` 做了什么

它的规则很直接：

1. 如果订单还没有 nonce，就先预留并落库
2. 如果订单已经有 nonce，就本轮继续复用

这就让“失败重试”第一次具备了稳定语义。

也就是说，系统不再是：

`每次重试都像新订单一样重新拿号`

而是变成：

`同一笔订单优先沿用自己已经占用过的 nonce`

这才符合链上执行系统的思路。

### 5. 广播失败不再直接判终态

Day20 里，提现广播失败后不再把订单推进成：

- `FAILED`

而是记录失败原因，并保持在：

- `PENDING_BROADCAST`

同时新增了：

- `markBroadcastRetryableFailure(String failReason)`

它表达的是：

`这次广播没成功，但订单依然属于“可以继续重试的待广播订单”`

这一步特别重要。

因为链上广播阶段和链上执行失败阶段，本来就不是一回事：

1. 广播失败，可能只是“交易还没发出去”
2. 回执失败，才更接近“链上真的执行失败了”

这两个阶段必须分开，否则后面账务和补偿都会非常难做。

### 6. 已有 nonce 的订单在重试时会继续复用

现在的广播任务已经具备这样的行为：

1. 扫描 `PENDING_BROADCAST` 订单
2. 如果订单已经有 nonce，就直接用这个 nonce 再次广播
3. 如果订单还没有 nonce，才为它分配一个新的 nonce

这就让 Day20 的广播任务从“只会广播一次”，升级成了：

`具备最小重试语义的顺序执行任务`

虽然还不是生产级，但方向已经非常正确。

### 7. 测试也同步补到了 Day20 语义

当前测试已经覆盖了：

1. 新订单广播前会预留 nonce，并在广播成功后记录 `txHash`
2. 已经预留过 nonce 的订单，重试时会继续复用原 nonce
3. 广播失败后，订单会保留在 `PENDING_BROADCAST`，并记录失败原因

这一点很重要，因为 Day20 改动的不只是参数签名，而是：

`提现执行状态机的行为语义`

没有测试把这些规则钉住，后面很容易被改回去。

## 四、Day20 之后，提现主链路发生了什么变化

到 Day20 为止，提现主链路已经从：

`审核通过 -> 直接尝试广播 -> 成功后等回执`

进一步演进成：

1. 用户发起提现申请
2. 校验余额并冻结 `amount + fee`
3. 创建 `withdraw_order`
4. 审核通过后进入 `PENDING_BROADCAST`
5. 广播任务先为订单分配或复用 `nonce`
6. 先把 `nonce` 预留到订单里
7. 如果广播成功，推进到 `BROADCAST_SUBMITTED`
8. 如果广播失败，保留在 `PENDING_BROADCAST` 等待下轮重试
9. 回执同步任务继续跟踪 `BROADCAST_SUBMITTED`
10. 链上成功则扣减冻结余额并写 `WITHDRAW_DEDUCT`
11. 链上失败则解冻回退并推进 `FAILED`

你会发现，Day20 真正补的不是“多一个分支”，而是：

`把提现执行链路从线性流程，往“可恢复任务”推进了一步`

这就是典型的 Web3 后端味道。

## 五、Day20 最值得记住的几个工程判断

### 1. nonce 不是“顺手记录”，而是提现执行的核心状态

很多人一开始会把 `nonce` 只当成广播返回值。

但 Day20 最关键的认知升级是：

`nonce 应该在广播前就进入订单状态机`

因为它不是“结果”，而是“执行计划的一部分”。

### 2. 广播失败不应该立刻等于订单失败

只要交易还没成功发到链上，很多失败都只是执行侧的临时异常。

所以更合理的做法是：

`记录失败原因，保留待广播状态，等待重试`

这比“立刻终态化”更符合真实钱包系统。

### 3. 失败重试优先复用原 nonce

这是 Day20 最核心的规则之一。

如果同一笔订单在重试时不断切换 nonce，会带来几个麻烦：

1. 链上顺序更难排查
2. 本地执行轨迹更混乱
3. 多笔订单更容易互相打架

所以第一版最稳妥的做法就是：

`订单有 nonce 就复用，没有才分配`

### 4. 节点视角和本地视角要一起看

只依赖节点的 pending nonce 不够，只依赖本地记录也不够。

Day20 现在做的是：

`节点建议 + 本地已预留最大 nonce`

两边一起参考。

这还不是终极方案，但已经比“单看一边”靠谱很多。

## 七、当前版本还没有做什么

虽然 Day20 已经把 nonce 和重试补到第一版，但一定要清楚，它还不是生产级方案。

当前仍然没有做的部分包括：

1. 分布式 nonce 锁
2. 多实例并发广播保护
3. 重试次数上限和退避策略
4. `replacement transaction` 策略
5. EIP-1559 动态费率
6. 热钱包余额检查
7. 广播失败告警
8. 链上回执长时间未返回的超时处理

所以当前最准确的表达应该是：

`我已经实现了提现 nonce 管理与广播重试第一版，能说明我理解了链上顺序控制、重试语义和本地状态机如何配合，但还没把它做成生产级执行系统`

这个说法会比“我已经做完了完整提现引擎”更专业、更可信。

## 八、从项目展示角度，Day20 的价值是什么

到了 Day20，这个仓库对外展示时，已经能比较清楚地体现出下面三层能力：

### 1. 你不只是会读链

你已经不只是：

- 连 RPC
- 扫日志
- 查回执

而是开始真正处理：

- 链上写入
- 交易顺序
- 重试策略

### 2. 你理解 Web3 后端和普通支付后端的差异

普通后端也会讲：

- 重试
- 幂等
- 状态机

但 Web3 后端多了非常具体的链上约束：

- nonce
- 广播与回执分离
- 节点视角与本地视角不一致

Day20 正是在补这部分差异。

### 3. 你已经在用“执行系统”的方式思考提现

也就是说，你不是在写一个简单接口，而是在写：

`待执行订单 -> 广播任务 -> 回执任务 -> 账务落地`

这样的任务驱动型链路。

这正是钱包后端、交易所出金后端非常看重的思维方式。

## 九、Day21 最合理的推进方向是什么

Day20 做完之后，下一步最合理的方向我会建议优先做：

`对账、补扫、链重组与失败补偿`

原因是：

1. 充值侧已经有扫描和入账，需要开始思考补扫与链重组
2. 提现侧已经有申请、审核、广播、回执和重试，需要开始补对账与失败补偿
3. 这一步会把项目从“单条执行链路”推进到“带运维和稳定性视角的钱包后端”

如果 Day19 和 Day20 更偏“把交易发出去”，那么 Day21 开始就更偏：

`把系统做得更稳、更可审计、更像真实资金后端`

## 阶段结论

Day20 的本质，不是多写了一个 `nonce` 字段，也不是多捕获了一次异常。

它真正补上的，是：

`提现执行里的最小顺序控制与最小重试语义`

更准确地说，到今天为止，这个项目已经形成了这样一条比较完整的资金执行主线：

`充值识别 -> 充值入账 -> 提现申请 -> 冻结余额 -> 审核 -> 预留 nonce -> 广播 -> 回执跟踪 -> 成功扣减 / 失败回退 / 广播失败重试`

这条链路虽然还没到生产级，但已经足以说明：

`这个仓库不再只是 Web3 学习笔记，而是在逐步长成一个能展示真实钱包后端思维的工程化项目。`
