# Day 18 - 提现审核与解冻回退第一版

今天进入 `Day 18`。

如果 `Day17` 解决的是：

`用户怎么发起提现申请，并把资金先冻结起来`

那么 `Day18` 解决的就是：

`后台怎么审核这笔提现，以及审核拒绝时怎么把钱安全退回去`

这一步非常关键，因为只会“申请 + 冻结”还不够，真正像后端工程的地方在于：

`系统能不能把冻结中的资金继续推进，或者在不满足条件时可靠回滚`

---

## 一、Day18 的核心目标是什么

提现链路里最容易被忽略的一步，就是“审核失败时怎么办”。

如果没有这一步，系统就会出现一个很糟糕的状态：

- 用户提交提现
- 平台冻结资金
- 但后面审核没通过
- 钱却一直冻着

这会直接导致账务异常。

所以 Day18 的目标可以概括成一句话：

`把提现订单从“待审核”推进到“审核通过待广播”或“审核拒绝并解冻回退”`

这条思路和传统支付、清结算、账务系统是一致的：

- 先受理
- 再审核
- 通过则继续执行
- 拒绝则回退冻结

---

## 二、为什么审核通过和审核拒绝不能只是改状态

很多 demo 做提现审核时，只会写：

- 审核通过：改个状态
- 审核拒绝：再改个状态

但真实资金系统里，这样是不够的。

尤其是审核拒绝时，如果只改订单状态，不回滚冻结余额，就会出现：

1. 订单显示已拒绝
2. 用户资金却仍然被冻结
3. 可用余额和冻结余额口径都错
4. 后续还很难对账

所以 Day18 最关键的工程判断是：

`审核拒绝一定要和解冻回退绑在一起`

这和充值场景里“看到链上日志不等于正式入账”是同一类思想：

`状态推进必须和账务动作绑定`

---

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经新增并打通了下面这些能力。

### 1. 增加后台提现审核接口

新增接口：

- `POST /admin/withdraw/review/approve`
- `POST /admin/withdraw/review/reject`

也就是说，当前项目已经把提现链路明确拆成了两层：

1. 用户侧申请入口
2. 后台侧审核入口

这个拆分非常重要，因为钱包后端和交易所后端的资金链路里，后台审核往往就是风险控制的核心承接点。

### 2. 提现订单状态和审核状态进一步细化

新增状态常量：

- `PENDING_BROADCAST`
- `REJECTED`
- `APPROVED`
- `REJECTED`（审核状态）

现在提现订单的状态语义已经比 Day17 更清晰了：

- `PENDING_REVIEW`
- `PENDING_BROADCAST`
- `REJECTED`

同时审核状态也开始具备独立表达能力：

- `PENDING`
- `APPROVED`
- `REJECTED`

这意味着后续再继续补广播、回执、失败回退时，状态承接会顺很多。

### 3. 审核通过推进到待广播状态

Day18 的审核通过逻辑不是直接发链上交易，而是：

`先把提现订单推进到待广播状态`

这样做的好处是：

1. 审核动作和链上执行动作解耦
2. 后面可以单独接定时任务或广播服务
3. 更符合真实后端里“审核”和“执行”分层的习惯

这一步看起来简单，但其实是很好的工程边界意识。

### 4. 审核拒绝时自动解冻余额

这是 Day18 最关键的落地能力。

当前审核拒绝时会做这几件事：

1. 查询对应提现订单
2. 查询余额主表
3. 校验冻结余额是否足够覆盖 `amount + fee`
4. 把冻结金额退回可用余额
5. 写一条解冻流水
6. 把提现订单推进为拒绝状态

也就是说，Day18 真正解决的是：

`提现回退动作开始具备账务语义`

### 5. 增加提现解冻流水

新增流水类型：

- `WITHDRAW_UNFREEZE`

为什么一定要加这条流水？

因为如果只改余额主表，你只能看到：

- 可用余额涨回来了
- 冻结余额降下去了

但你看不到：

- 是哪一笔提现被拒绝导致的
- 是什么时候解冻的
- 解冻金额是多少

所以 Day18 的解冻流水，其实是后续对账和排障的关键资料。

### 6. 提现响应增加审核人和审核时间

`WithdrawOrderResponse` 现在已经补上了：

- `reviewBy`
- `reviewTime`

这一步虽然不是资金动作本身，但对后台管理和项目展示很有帮助。

因为它让“审核”不再只是一个抽象状态，而是真正变成了：

`谁在什么时间做了什么动作`

这就是更像真实后端的地方。

---

## 四、当前提现主链路已经走到哪一步了

到 Day18 为止，提现主链路已经可以这样理解：

1. 用户提交提现申请
2. 校验余额是否足够
3. 冻结 `amount + fee`
4. 创建 `withdraw_order`
5. 状态记为 `PENDING_REVIEW`
6. 后台审核通过，则推进到 `PENDING_BROADCAST`
7. 后台审核拒绝，则把冻结余额退回可用余额
8. 写入 `WITHDRAW_UNFREEZE` 流水
9. 订单状态推进为 `REJECTED`

也就是说，当前项目已经不只是“会受理提现申请”，而是：

`开始具备提现审核和资金回退能力`

这一步对钱包后端来说是非常关键的工程分水岭。

---

## 五、Day18 学到的最重要的工程判断

### 1. 审核是业务控制点，不是展示字段

很多时候，系统里加一个“审核状态”很容易流于表面。

但在资金后端里，审核真正有价值的地方在于：

- 决定这笔资金能不能继续往下执行
- 决定冻结资金是否应该被回退

所以审核不只是一个标签，而是状态机的关键分支点。

### 2. 状态推进一定要带余额动作

Day18 里最重要的一点，就是把：

- 订单状态
- 余额主表
- 账户流水

绑在一起看。

这也是为什么审核拒绝不能只改订单状态。

### 3. 审核通过和广播执行必须分层

审核通过后，当前版本只推进到：

- `PENDING_BROADCAST`

而没有立刻去发链上交易。

这个设计是对的，因为它给后续预留了很清晰的职责边界：

- 审核决定是否允许出金
- 广播负责真正执行链上动作
- 回执跟踪负责确认链上结果

这是非常标准的后端分层思路。

### 4. 解冻流水和冻结流水一样重要

很多系统会认真记冻结，却忽略了解冻。

但对账和审计时，真正重要的是：

`每一次余额形态变化都必须能追出来`

所以有：

- `WITHDRAW_FREEZE`
- `WITHDRAW_UNFREEZE`

这两类流水，项目的账务表达才开始完整。

## 六、当前版本还没做什么

虽然 Day18 已经把审核和拒绝回退补出来了，但提现链路仍然没有完全做完。

当前还没做的部分包括：

1. 广播链上交易
2. nonce 管理
3. 链上回执跟踪
4. 广播失败后的回退
5. 提现成功后的真正扣减
6. 热钱包 / 签名服务 / 风控扩展

所以当前最准确的表达应该是：

`我已经完成提现申请、冻结、审核通过待广播，以及审核拒绝解冻回退的第一版闭环`

而不是：

`我已经做完完整提现系统`

---

## 七、从项目展示角度，Day18 的价值是什么

到了 Day18，这个仓库的资金主线已经明显更完整了。

现在你已经可以讲出：

### 1. 充值主线

`候选充值识别 -> 确认数推进 -> 正式入账 -> 余额更新 -> 入账流水`

### 2. 提现主线

`提现申请 -> 冻结余额 -> 提现订单 -> 审核通过待广播 / 审核拒绝解冻 -> 冻结流水 / 解冻流水`

这对“8 年 Java 后端转 Web3 后端”的表达非常有帮助。

因为这已经开始像一个真正的资金后端项目，而不是单纯的链接口 demo。

## 八、进入下一阶段前，要记住的 6 句话

1. Day17 解决的是“提现怎么受理”，Day18 解决的是“提现怎么审核和回退”。
2. 审核拒绝如果不解冻余额，账务一定会出问题。
3. 审核通过不等于链上已广播，只是进入待执行状态。
4. `withdraw_order` 现在已经开始承担真正的状态承接职责。
5. `WITHDRAW_FREEZE` 和 `WITHDRAW_UNFREEZE` 一起构成了最小提现账务轨迹。
6. 当前项目已经具备了比较完整的入金主线和提现前半段闭环。

---

## 九、Day19 最合理的推进方向是什么

在 Day18 之后，最顺的下一步是继续往链上执行侧推进：

1. 预留广播网关
2. 增加提现广播任务
3. 管理 nonce
4. 跟踪回执
5. 成功后扣减冻结余额
6. 失败后自动解冻回退

如果只选一个最值钱的方向，我会建议优先做：

`广播前状态推进 + 广播失败回退预案`

因为这样提现链路就会真正进入“链上执行型后端”的阶段。

## 阶段结论

Day18 标志着这个仓库已经不再只是：

- 会识别充值
- 会正式入账
- 会受理提现申请

而是进一步具备了：

`提现审核与资金回退`

更准确地说，当前项目已经形成了下面这条更完整的资金主线：

`充值识别 -> 充值入账 -> 余额更新 -> 提现申请 -> 冻结余额 -> 审核通过待广播 / 审核拒绝解冻`

这条主线虽然还没延伸到真正链上广播，但已经足够说明：

`这个仓库正在逐步长成一个真正有资金状态流转语义的钱包后端 demo。`
