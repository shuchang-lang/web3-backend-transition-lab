# Day 19 - 提现广播与回执跟踪第一版

今天进入 `Day 19`。

如果 `Day18` 解决的是：

`提现申请之后，后台怎么审核和解冻回退`

那么 `Day19` 真正开始推进的，就是提现链路里更接近 Web3 后端本质的部分：

`把审核通过的提现订单推进到链上广播，并根据链上回执决定成功扣减还是失败回退`

这一步很关键，因为从这里开始，项目才真正进入：

`链上执行型后端`

---

## 一、Day19 的核心目标是什么

在前面的阶段里，提现链路已经具备：

1. 用户申请
2. 余额冻结
3. 提现订单承接
4. 后台审核通过 / 拒绝
5. 审核拒绝解冻

但这时系统还没有真正做一件最关键的事：

`把提现动作发到链上`

所以 Day19 的目标可以概括成一句话：

`把提现订单从“待广播”推进到“已广播待回执”，再根据回执决定成功扣减或失败回退`

这一步本质上就是把：

- 内部订单系统

和：

- 链上执行世界

真正连接起来。

---

## 二、为什么广播和回执跟踪必须单独分层

很多人做链上提现时会下意识写成：

`审核通过 -> 立刻发交易 -> 立刻认为成功`

但真实后端通常不能这么粗暴。

因为链上执行至少还分两步：

1. 节点接受了广播
2. 交易真的上链并执行成功

这两步不是一回事。

所以 Day19 里，提现链路被明确拆成了两个任务：

1. `broadcast`
2. `receipt sync`

这个拆分非常重要，因为后面你几乎一定会需要：

- 定时重试
- 回执补拉
- 广播失败告警
- nonce 管理
- 待执行队列

如果现在就把广播和回执混成一坨，后面一定难扩。

---

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经新增并打通了下面几块能力。

### 1. Web3Gateway 增加提现广播与回执能力

`Web3Gateway` 现在不只负责读链，还新增了：

- 是否支持提现广播
- 广播 ERC-20 提现交易
- 查询提现交易回执

并新增了对应结果对象：

- `WithdrawBroadcastResult`
- `WithdrawTransactionReceiptResult`

这一步非常重要，因为它意味着：

`提现执行层没有直接依赖 web3j，而是仍然走统一的链交互边界`

也就是说，项目没有因为进入写链阶段就破坏之前立好的架构边界。

### 2. web3j 网关开始具备最小 ERC-20 广播能力

`Web3jWeb3Gateway` 当前已经支持最小版本的 ERC-20 提现广播：

1. 读取热钱包 nonce
2. 读取节点 gasPrice
3. 编码 ERC-20 `transfer`
4. 使用私钥签名
5. 调用 `eth_sendRawTransaction`

同时还支持：

- `eth_getTransactionReceipt`

去拉提现交易回执。

这说明项目已经从“只会扫链”推进到了：

`开始真正对链上发起交易并追踪结果`

### 3. 增加提现广播配置

新增配置：

- `WEB3_WITHDRAW_HOT_WALLET_PRIVATE_KEY`
- `WEB3_WITHDRAW_CHAIN_ID`
- `WEB3_WITHDRAW_GAS_LIMIT`

并且默认策略是：

`如果没配广播私钥，就自动跳过广播任务`

这点很实用，因为它保证了：

- 仓库在本地没配热钱包时依然能跑
- 学习阶段不会被强行卡死在真实链上执行
- 但结构已经为真实执行准备好了

### 4. 新增提现执行服务

新增：

- `WithdrawExecutionAppService`
- `WithdrawExecutionTask`

当前执行链路分成两段：

#### 广播任务

只处理：

- `PENDING_BROADCAST`

广播成功后推进到：

- `BROADCAST_SUBMITTED`

并记录：

- `txHash`
- `nonce`

#### 回执同步任务

只处理：

- `BROADCAST_SUBMITTED`

如果链上成功：

- 扣减冻结余额
- 写提现扣减流水
- 推进订单为 `SUCCESS`

如果链上失败：

- 解冻回可用余额
- 写解冻流水
- 推进订单为 `FAILED`

这一步之后，提现链路终于从“内部状态机”真正走到了“链上执行结果驱动的状态机”。

### 5. 新增提现成功扣减流水

新增流水类型：

- `WITHDRAW_DEDUCT`

为什么要有这条流水？

因为当提现链上成功时，系统需要表达的不只是：

- 订单成功了

还要表达：

- 那笔之前冻结的资金已经被正式扣走

这和：

- `WITHDRAW_FREEZE`
- `WITHDRAW_UNFREEZE`

一起，基本构成了最小提现账务轨迹。

### 6. 提现订单状态继续细化

新增状态：

- `BROADCAST_SUBMITTED`
- `SUCCESS`
- `FAILED`

这说明提现订单已经不只是“审核状态机”，而开始具备：

`链上执行状态机`

这对后续扩展：

- 多次广播重试
- 回执延迟
- 失败补偿
- 审计排查

都会更有帮助。

---

## 四、当前提现主链路已经长什么样了

到 Day19 为止，提现主链路已经可以概括成：

1. 用户发起提现申请
2. 校验余额并冻结 `amount + fee`
3. 创建 `withdraw_order`
4. 后台审核通过或拒绝
5. 拒绝则解冻回退
6. 通过则进入 `PENDING_BROADCAST`
7. 广播任务提交链上交易
8. 订单推进到 `BROADCAST_SUBMITTED`
9. 回执同步任务查询链上结果
10. 成功则扣减冻结余额并写 `WITHDRAW_DEDUCT`
11. 失败则解冻回退并写 `WITHDRAW_UNFREEZE`

这条链路已经非常像一个真正的钱包后端了。

虽然还没有多次重试、告警和生产级 nonce 锁，但主线已经走出来了。

## 五、Day19 学到的最重要的工程判断

### 1. 节点接受广播，不等于链上执行成功

这应该是 Day19 最值得记住的一句话。

广播成功只能说明：

`节点接受了这笔交易`

但真正决定账务结果的是：

`链上回执`

所以提现执行一定不能在 `eth_sendRawTransaction` 成功后就直接扣账。

### 2. 提现成功扣减和提现失败回退都必须落账务动作

Day19 里最关键的不是多了几个状态，而是：

- 成功会扣减冻结余额
- 失败会回退冻结余额

也就是说，链上结果开始真正驱动账务变化。

### 3. 广播和回执同步要拆成两个任务

这个拆分会让系统天然更适合：

- 定时调度
- 重试补偿
- 运维排查
- 批量处理

这一步其实已经开始有“交易所 / 钱包执行系统”的味道了。

### 4. 热钱包私钥和链上写入一定要放在边界层

Day19 虽然增加了真实广播能力，但依然没有把私钥和签名逻辑写进业务层。

这非常重要。

因为后面你很可能还会换成：

- 独立签名服务
- 托管钱包服务
- MPC
- HSM

如果现在边界没立住，后面会非常痛苦。

## 六、当前版本还没做什么

虽然 Day19 已经把广播和回执跟踪补出来了，但依然只是第一版。

当前还没有做的部分包括：

1. nonce 锁与并发保护
2. EIP-1559 费用策略
3. 广播失败后的自动重试队列
4. 回执超时补扫
5. 提现批次控制
6. 热钱包余额监控
7. 风控与限额体系

所以现在最准确的表达应该是：

`我已经完成提现从审核通过到链上广播、回执跟踪、成功扣减和失败回退的第一版闭环`

而不是：

`我已经做完了生产级提现执行系统`

到了 Day19，这个仓库已经不再只是“钱包后端骨架 + 资金状态流转 demo”。

它已经开始具备：

`真实链上执行型后端`

### 1. 充值执行侧

`扫描日志 -> 确认数推进 -> 正式入账`

### 2. 提现受理侧

`提现申请 -> 冻结余额 -> 审核`

### 3. 提现执行侧

`广播 -> 回执跟踪 -> 成功扣减 / 失败回退`

这对 GitHub 展示和面试表达都非常有价值。

## 八、进入下一阶段前，要记住的 6 句话

1. Day18 解决的是“审核和解冻回退”，Day19 解决的是“链上广播和回执驱动账务结果”。
2. 广播成功不等于提现成功，真正的账务依据是交易回执。
3. `BROADCAST_SUBMITTED` 是提现执行链路里非常关键的中间状态。
4. `WITHDRAW_DEDUCT` 让提现成功后的账务语义开始完整。
5. 提现失败时回退冻结余额，是链上执行后资金一致性的核心动作。
6. 当前项目已经开始明显具备“链上执行型后端”的工程结构。

## 九、Day20 最合理的推进方向是什么

在 Day19 之后，最值得继续推进的方向有两个：

1. nonce 锁、重试和更稳的广播策略
2. 对账、补扫、监控和告警

如果只选一个最适合作为下一步，我会建议优先做：

`nonce 管理与广播重试`

因为这是提现执行链路里最容易在真实环境里踩坑的部分，也是 Web3 后端和普通后端差异非常明显的一块。
