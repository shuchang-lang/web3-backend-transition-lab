`Day 3 的核心，就是搞懂“链上代码怎么跑、跑完后后端怎么看结果”。`

***

**一、先建立整体画面**

你可以把一笔合约交易想成这样：

1.  用户用 `EOA（外部账户）` 发起交易
2.  交易被广播到链上
3.  节点用 `EVM（以太坊虚拟机）` 执行合约代码
4.  合约可能会：
    *   改 `storage（持久化状态）`
    *   转账
    *   调别的合约
    *   发出 `event log（事件日志）`
5.  后端再通过 `RPC（远程调用接口）` 去查交易结果和日志

你做 Java 后端时，习惯的是：

*   请求进 Controller
*   调 Service
*   写 DB
*   记录日志

链上也有点像，只是“执行者”不再是你公司的单个服务，而是`全网节点共同执行同一段合约逻辑`。

***

**二、EVM 到底是什么**

`EVM（以太坊虚拟机）`，你先把它理解成：

`以太坊上运行智能合约的统一执行环境`

它的作用是：

*   读取交易里的调用信息
*   执行合约字节码
*   修改链上状态
*   计算这次执行消耗了多少 `gas（链上执行消耗）`
*   产出执行结果和日志

你可以类比成：

`JVM（Java 虚拟机）` 是 Java 代码运行环境\
`EVM` 是 Solidity 合约运行环境

但它和 JVM 有个很大的不同：

*   JVM 通常只是你服务器自己执行
*   EVM 是所有节点都要按同样规则执行，结果必须一致

所以 `EVM` 更强调：

*   确定性
*   可复现
*   状态一致

这就是为什么链上开发限制会更多，成本也更高。

***

**三、合约是怎么执行的**

假设你调用一个 `ERC20（同质化代币标准）` 合约的 `transfer` 方法。

链上的实际过程大概是：

1.  你构造交易
2.  `to` 指向 token 合约地址
3.  `data` 里放编码后的 `transfer(接收方, 金额)`
4.  节点拿到交易后，交给 `EVM` 执行
5.  `EVM` 根据合约代码判断：
    *   余额够不够
    *   要不要扣发送方余额
    *   要不要加接收方余额
6.  执行成功后：
    *   更新状态
    *   发出 `Transfer` 事件日志
    *   生成 `receipt（交易回执）`

你后端以后做监听时，很多时候不是“调用合约”，而是“消费这次执行的结果”。

***

**四、三种数据区域：storage / memory / calldata**

这是 Day 3 最重要的一块。

**1. `storage（持久化存储）`**
这是合约真正长期保存数据的地方。

比如：

*   用户余额
*   授权额度
*   总供应量
*   订单状态

特点：

*   写进去之后会长期保存在链上
*   修改它最贵，消耗的 `gas` 更多
*   类似数据库里的正式业务数据

你可以把它类比成：

`MySQL 表里的持久化字段`

***

**2. `memory（临时内存）`**
这是合约执行过程里的临时变量区。

特点：

*   只在当前函数执行期间有效
*   执行结束后就没了
*   比 `storage` 便宜

类比：

`Java 方法里的局部变量 / 堆内临时对象`

比如你在函数里临时组装一个数组、临时做计算，这些通常会在 `memory` 里。

***

**3. `calldata（调用参数）`**
这是外部调用传给合约的输入数据。

比如：

*   调 `transfer(to, amount)`
*   这里的 `to` 和 `amount` 就来自 `calldata`

特点：

*   只读
*   由外部调用带进来
*   通常比复制到 `memory` 更省

类比：

`Controller 接口收到的入参`

所以你可以这样记：

*   `storage`：像数据库正式数据
*   `memory`：像函数执行时的临时变量
*   `calldata`：像外部请求传进来的参数

***

**五、event log 到底是什么**

`event log（事件日志）`，你可以理解成：

`合约执行过程中主动打出来的结构化业务日志`

比如 ERC20 转账成功后，合约通常会发一个：

*   `Transfer(from, to, amount)`

这个日志不会替代正式状态，但它非常适合被后端系统监听。

你可以把它类比成：

`业务代码里打的结构化操作日志 / MQ 事件通知`

但它和普通日志又不完全一样：

*   它是链上执行结果的一部分
*   会跟着交易一起被写进区块
*   可以通过节点按条件查询和过滤

所以后端特别喜欢拿它做：

*   充值监听
*   交易索引
*   数据同步
*   通知触发

***

**六、为什么后端特别关心 event log**

这是你做 Web3 后端最关键的理解之一。

因为后端很多时候不是直接去“猜”合约状态变化，而是去“消费合约发出来的确定结果”。

比如充值到账识别：

如果你只是看“某笔交易发给了谁”，可能不够，因为：

*   交易可能是调用合约，不是直接转原生币
*   `value` 可能是 0
*   真正的 token 转账信息在 `event log` 里

所以后端监听 ERC20 充值，常见做法是：

1.  扫新区块
2.  查目标合约的 `Transfer` 日志
3.  过滤接收地址是不是平台托管地址
4.  落库
5.  等 `confirmation（确认数）` 足够后再入账

你可以把这理解成：

`日志驱动的数据同步`

这和你熟悉的：

*   Binlog 订阅
*   MQ 消费
*   操作流水落库

其实思路很像。

***

**七、receipt 是什么，为什么后端也要看它**

`receipt（交易回执）` 可以理解成：

`这笔交易执行后的结果单`

它通常会告诉你：

*   交易成功还是失败
*   消耗了多少 gas
*   所属区块
*   产生了哪些日志

所以后端看链上交易，往往不只是看交易本身，还会看：

*   `transaction（交易原文）`
*   `receipt（执行结果）`
*   `event log（事件日志）`

你可以简单记成：

*   `transaction`：请求
*   `receipt`：执行结果
*   `event log`：业务事件输出

***

**八、用 Java 后端思维串起来**

你可以这样类比：

`Web2`

*   请求进 Controller
*   调 Service
*   改数据库
*   写操作日志
*   下游系统消费日志

`Web3`

*   用户签名发交易
*   `EVM` 执行合约
*   改 `storage`
*   发 `event log`
*   后端通过 `RPC` 查询 / 监听日志并落库

所以链上后端的一个核心工作，本质上就是：

`把链上的执行结果，同步成你业务系统能消费的数据`

***

**九、今天最该记住的 6 句话**

1.  `EVM` 是执行智能合约的统一运行环境。
2.  合约执行后，不只是改状态，还可能发出 `event log`。
3.  `storage` 是持久化数据，`memory` 是临时数据，`calldata` 是外部调用入参。
4.  `event log` 很适合后端做监听和索引。
5.  后端看链上结果，通常要同时看交易、回执、日志。
6.  充值监听、索引服务，本质上都是在消费链上执行后的结果。
