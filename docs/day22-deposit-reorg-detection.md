# Day 22 - 充值链路 reorg 风险识别第一版

今天进入 `Day 22`。

如果 `Day21` 解决的是：

`漏扫以后怎么手动补扫，以及余额主表怎么做最小对账`

那么 `Day22` 开始补的，就是钱包后端里一个非常关键、但很多学习项目都会跳过的问题：

`链重组以后，之前扫到并入账的充值记录还算不算有效`

这一步非常重要。

因为只要项目开始真正处理链上充值，就一定绕不开：

`reorg（链重组）`

---

## 一、为什么 Day22 要优先补 reorg

对于传统 Java 后端来说，你可能更习惯下面这种思路：

`消息消费到了 -> 落库 -> 业务推进`

但链上充值不是普通 MQ 消息。

链上的 `event log（事件日志）` 是依附在区块上的。

也就是说，只要区块本身发生回滚，日志就可能跟着失效。

这就是 `reorg` 最值得警惕的地方：

`你昨天看见的充值日志，今天未必还在那条最终链上`

如果一个钱包后端只会：

1. 扫到充值日志
2. 达到确认数后入账

但不会处理：

3. 充值后来疑似因为链重组而失效

那它就还没有真正进入链上资金系统的世界。

所以 Day22 的第一目标不是补偿，而是先把问题识别出来：

`先知道哪条充值记录可能有风险`

---

## 二、Day22 第一版的边界是什么

链重组完整处理其实很大，至少可以拆成两步：

1. 风险识别
2. 资金补偿

Day22 我先只做第一步：

`reorg 风险识别与标记`

也就是说，这一版先不直接做：

- 余额冲正
- 资金回退
- 自动补偿

而是先做到：

1. 检查历史充值记录对应的链上日志是否还存在
2. 如果发现异常，就把充值记录标成 `REORG_SUSPECTED`
3. 把“发现问题”和“修复问题”拆成两个阶段

这个边界很合理。

因为对于资金系统来说，发现风险和直接动钱，应该是两层不同决策。

---

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经补了下面几块能力。

### 1. Web3Gateway 增加充值日志链上核验能力

`Web3Gateway` 新增了两项能力：

- `supportsDepositReorgCheck()`
- `inspectDepositTransferLog(...)`

这一步的意义在于：

`充值 reorg 检查依然走统一链交互边界，而不是让业务层直接依赖 web3j`

这点很重要。

因为这样后面如果你从：

- 本地 `web3j`

切到：

- 托管节点服务
- 专门的链数据服务
- 内部索引网关

业务层还是可以保持稳定。

### 2. 新增标准化结果对象 `DepositLogChainCheckResult`

新增：

- `DepositLogChainCheckResult`

它把充值日志检查结果先统一抽象成三类：

1. `PRESENT`
2. `REORG_SUSPECTED`
3. `UNSUPPORTED`

为什么要多一层结果对象，而不是业务层直接处理各种异常？

因为 Day22 开始，项目已经不只是“链交互 demo”，而是在做：

`链上风险判断`

这类逻辑如果直接散在业务层里，后面会很难维护。

### 3. web3j 网关增加最小链上核验逻辑

`Web3jWeb3Gateway` 当前第一版会检查三件事：

1. 交易回执是否还存在
2. 回执区块号是否仍然等于业务侧记录的区块号
3. 回执日志里是否还能找到对应的 `logIndex` 和代币合约地址

只要这三步里有一步不成立，就会返回：

- `REORG_SUSPECTED`

这三类场景其实就已经覆盖了最典型的第一版风险：

#### 场景 1：回执已经查不到

这通常意味着：

`之前业务侧看见的链上交易，现在节点已经找不到它的确认结果`

这很可能就是链重组或节点视角变化后的异常现象。

#### 场景 2：区块号已经变了

如果业务侧当时记录的是某个区块号，但链上回执返回的区块号已经换了，
那说明这笔交易至少不是原来那个链位置了。

对充值记录来说，这就是一个很典型的：

`需要人工复核的信号`

#### 场景 3：回执里找不到原始日志

哪怕交易还存在，如果原来的目标日志已经不在回执里了，
那也不能继续把它当成完全可信的充值依据。

这一步开始体现出一个很重要的工程判断：

`充值是否有效，看的不只是 txHash 还在不在，而是原始充值日志还在不在`

### 4. 充值记录新增 `REORG_SUSPECTED` 状态

`DepositStatusConstants` 新增了：

- `REORG_SUSPECTED`

并且 `DepositRecord` 增加了：

- `markReorgSuspected()`

这一步非常关键。

因为从 Day22 开始，充值记录已经不只是：

- `PENDING_CONFIRM`
- `CREDITED`

两段式状态了。

它开始具备：

`链上风险状态`

这对后续扩展下面这些能力都很有帮助：

- 人工复核
- 冲正补偿
- 风险拦截
- 运维排查

### 5. 新增充值链重组检查任务 `DepositReorgCheckTask`

新增：

- `DepositReorgCheckTask`

当前它会检查：

- `PENDING_CONFIRM`
- `CREDITED`

这两类充值记录。

原因很直接：

1. 待确认充值本来就在链上稳定性观察期
2. 已入账充值如果后来出现异常，则更值得重点关注

当前任务逻辑很清晰：

1. 扫描待检查充值记录
2. 调用网关检查链上日志是否仍然成立
3. 如果存在风险，则把状态推进成 `REORG_SUSPECTED`
4. 记录告警日志

这一步之后，系统已经第一次具备了：

`充值风险巡检`

的雏形。

### 6. 新增后台接口

新增接口：

- `POST /admin/deposit/reorg/check/run`

这意味着 Day22 之后，后台已经能手动触发一轮：

`充值链重组风险检查`

这很像真实后台运维工具的第一版能力。

因为很多时候链上风险处理并不会先从“自动补偿”开始，
而是先从：

`人工触发检查 -> 发现风险记录 -> 再决定后续处置`

开始。

### 7. 测试也同步补到了 Day22 语义

当前测试已经覆盖：

1. 未配置真实核验能力时，任务会跳过
2. 当链上日志缺失时，充值记录会被标记成 `REORG_SUSPECTED`
3. 当链上日志仍然存在时，充值记录不会被误改
4. 控制器接口可以正常触发 reorg 检查任务

到这里为止，当前项目测试总数已经推进到：

`34`

这说明 Day22 不是只补了概念文档，而是真正落了代码和测试。

## 四、Day22 之后，充值链路发生了什么变化

到 Day22 为止，充值主链路已经不再只是：

`扫日志 -> 候选充值 -> 确认数推进 -> 正式入账`

它开始多了一条新的后台巡检线：

1. 扫描充值日志
2. 候选充值落库
3. 确认数推进
4. 正式入账
5. 后台对历史充值记录做链上核验
6. 发现异常时标记 `REORG_SUSPECTED`

这条线虽然还没有直接补偿资金，但它已经把项目推进到了：

`开始感知链上历史数据可能变化`

这一步是非常关键的。

## 五、Day22 最值得记住的几个工程判断

### 1. 充值是否有效，不能只看当时扫到了什么

这应该是 Day22 最值得记住的一句话。

你扫到充值日志，只能说明：

`在那个时刻、那个链视角下，这条日志存在`

但它不一定代表：

`这条日志永远有效`

这就是链上系统和普通数据库系统最大的不同之一。

### 2. 风险识别和资金补偿要拆开

Day22 第一版没有直接做冲正，是一个很好的边界控制。

因为对资金系统来说，最危险的事情之一就是：

`一发现异常就立刻动钱`

更稳妥的做法通常是：

1. 先识别风险
2. 先标记状态
3. 再进入补偿或人工复核

Day22 正是在做第一步。

### 3. reorg 检查不该只看交易还在不在

这是一个很容易被忽略的点。

如果只查：

- `txHash` 有没有回执

还不够。

因为对充值来说，真正关键的是：

- 原始日志还在不在
- 区块位置有没有变

Day22 已经把这个判断补到了第一版。

### 4. Day22 会故意制造“账务不一致信号”

这其实是一个很好的设计结果。

如果某条原本 `CREDITED` 的充值后来被标记成：

- `REORG_SUSPECTED`

但你还没有做 Day23 的冲正补偿，
那当前账户对账就可能出现不一致。

这不是坏事。

恰恰说明项目开始真实地表达：

`资金系统发现风险后，业务记录和余额结果之间会出现需要补偿的中间状态`

这非常符合真实场景。

## 七、当前版本还没有做什么

虽然 Day22 已经能识别 reorg 风险，但还没有做：

1. 自动冲正
2. 余额回退
3. 风险冻结
4. 对账结果联动补偿
5. reorg 风险结果落库审计
6. 更深层区块回滚策略

所以当前最准确的表达应该是：

`我已经实现了充值链路 reorg 风险识别第一版，系统能发现并标记异常充值，但还没有进入自动补偿阶段`

这个表述会比“我已经完整解决链重组问题”更真实、更专业。

到了 Day22，这个仓库对外展示时已经可以明显体现：

- 区块回滚

### 3. 你不是只会跑 happy path

`异常链路治理`

这对 GitHub 展示和面试都非常加分。

Day22 的本质，不是多了一个后台任务，也不是多加了一个状态。

它真正补上的，是：

`充值链路里的最小链重组风险感知能力`

更准确地说，到今天为止，这个项目已经形成了这样一条更完整的主线：

`充值识别 -> 确认入账 -> 提现申请 -> 冻结 -> 审核 -> nonce 预留 -> 广播 -> 回执跟踪 -> 手动补扫 -> 资产对账 -> reorg 风险识别`

这条主线虽然还没有做到自动补偿，但已经足以说明：

`这个仓库正在从“会跑主链路的钱包 demo”，继续长成“理解链上异常治理的钱包后端工程项目”。`
