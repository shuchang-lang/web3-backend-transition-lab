# Day 21 - 手动补扫与最小资产对账第一版

今天进入 `Day 21`。

如果 `Day20` 解决的是：

`提现广播时的 nonce 预留、失败重试和最小顺序控制`

那么 `Day21` 开始补的，就是一个真实钱包后端绕不过去的运维与稳定性视角：

`出问题以后，怎么补扫，怎么对账`

这一步非常重要。

因为一个只会“正常跑主链路”的钱包后端，还不能算真正可维护。

真正的资金后端一定还要回答两类问题：

1. 某段区块之前没扫到，怎么补回来
2. 当前余额主表到底和业务记录、流水快照是不是一致

Day21 的第一版，就是把这两件事先做成最小可运行能力。

---

## 一、为什么 Day21 要先做补扫和对账

到 Day20 为止，这个项目已经有了两条比较完整的资金主线：

### 1. 充值主线

`扫描日志 -> 候选充值 -> 确认数推进 -> 正式入账`

### 2. 提现主线

`提现申请 -> 冻结 -> 审核 -> 广播 -> 回执 -> 成功扣减 / 失败回退`

但真实环境里，主链路跑通只是第一步。

更常见的麻烦往往出现在这些地方：

- 某次 RPC 抖动导致一段区块没扫干净
- 人工修复后需要回放一段历史区块
- 余额主表被怀疑和流水、业务表不一致
- 冻结余额和待完成提现订单的金额对不上

也就是说，从 Day21 开始，项目关注点从：

`怎么把交易流程跑通`

开始转向：

`怎么把系统做得更稳、更容易排查`

这正是钱包后端、交易所后端很核心的能力。

---

## 二、Day21 第一版的范围怎么收敛

“补扫、对账、链重组、失败补偿”这个主题其实很大。

如果一下子全做，很容易把项目做散。

所以 Day21 我先只落两件最小但很有代表性的能力：

1. 手动补扫指定区块区间
2. 查询指定用户资产的最小对账结果

这两个能力先补出来，能解决三类非常典型的问题：

1. 扫描漏了一段区块时，能人工回放
2. 不影响正常的 `chain_scan_progress` 断点推进
3. 能快速看出“余额主表 / 流水 / 业务表 / 冻结订单”是不是同一个结果

这就是 Day21 第一版最重要的边界。

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经补上了下面这些能力。

### 1. 新增手动补扫任务 `DepositRescanTask`

新增：

- `DepositRescanTask`

它专门处理：

`指定区块区间回放`

这和日常扫描任务是分开的。

这里最关键的设计点不是“多扫一次”，而是：

`补扫不能污染正常扫描断点`

所以 Day21 的手动补扫任务只做三件事：

1. 按请求区间读取 ERC-20 `Transfer event`
2. 识别候选充值并幂等落库
3. 顺带刷新确认数并推进正式入账

但它不会更新：

- `chain_scan_progress`

这点非常重要。

因为人工补扫和正常断点推进，通常应该是两条分开的操作线。

否则一次人工补扫就可能把定时扫描的断点改乱。

### 2. 手动补扫支持“自动裁剪到最新区块”

补扫请求现在支持：

- `fromBlock`
- `toBlock`

如果你传入的结束区块大于当前链头，系统不会直接报错，而是会：

`自动裁剪到当前 latestBlock`

这样做的好处是：

1. 后台补扫体验更顺
2. 不需要人工先去算当前链头
3. 对临时回放区间更友好

同时返回结果里也会明确告诉你：

- 请求区间
- 实际补扫到的区块
- 当前链头
- 检测到的候选充值数量
- 推进完成的正式入账数量

这让补扫结果开始具备“任务反馈”能力。

### 3. 新增手动补扫接口

新增接口：

- `POST /admin/deposit/rescan/run`

它的作用是：

`让后台可以手动回放一段区块区间，而不是只能依赖固定断点往前扫`

这对以后扩展下面这些能力也很有帮助：

- 漏单排查
- 补扫脚本
- 链重组回放
- 历史数据重建

也就是说，Day21 虽然只是第一版，但接口边界已经开始像一个真实后台工具了。

### 4. 新增账户资产对账服务 `AccountReconcileAppService`

新增：

- `AccountReconcileAppService`

这个服务不是直接改账，而是做：

`最小一致性核对`

它当前会从 4 个视角看同一份资产：

1. `account_balance` 余额主表
2. `account_bill` 账户流水
3. `deposit_record` 已入账充值记录
4. `withdraw_order` 提现订单

这一步非常关键，因为 Day21 不是在做“报表展示”，而是在做：

`最小对账诊断`

### 5. 对账第一版实际核对了哪几件事

当前对账接口会给出下面几类结果。

#### 第一类：余额主表和业务表汇总是否一致

系统会计算：

- 已正式入账充值总额
- 已成功提现总额

然后得到业务表口径下的期望总资产：

`creditedDepositAmount - successfulWithdrawAmount`

再去和：

`availableBalance + frozenBalance`

做比对。

这一步相当于回答：

`如果只看充值已入账和提现已成功，当前总资产是不是合理`

#### 第二类：余额主表和资产口径流水是否一致

这里特别注意了一点：

`WITHDRAW_FREEZE` 和 `WITHDRAW_UNFREEZE` 不应该直接计入总资产变化`

因为冻结和解冻只是在：

- 可用余额
- 冻结余额

之间搬移，不改变总资产。

所以当前对账里，真正参与总资产净额计算的流水只有：

- `DEPOSIT_CREDIT`
- `WITHDRAW_DEDUCT`

这个判断很重要。

它说明项目开始区分：

`余额结构变化`

和：

`总资产变化`

这正是资金系统里很关键的账务口径意识。

#### 第三类：余额主表和最新流水快照是否一致

当前每次记流水时，都会把：

- `available_after`
- `frozen_after`

带上。

所以 Day21 第一版直接利用这点，去校验：

`余额主表当前快照，是否和最新一条流水快照一致`

这类核对非常有价值。

因为很多时候，哪怕总资产没问题，余额结构也可能出问题。

比如：

- 可用和冻结分布不一致
- 资金总数对，但冻结状态错了

这类问题只看总资产是发现不了的。

#### 第四类：冻结余额和待完成提现总额是否一致

这是 Day21 里我很建议你记住的一条核对思路。

系统会把下面这些状态的提现订单金额汇总起来：

- `PENDING_REVIEW`
- `PENDING_BROADCAST`
- `BROADCAST_SUBMITTED`

口径统一按：

`amount + fee`

然后拿它去和：

- `account_balance.frozen_balance`

做对比。

这一步本质上是在回答：

`当前冻结余额，是不是都能在待完成提现订单里找到来源`

这对钱包后端、交易所后端都很重要。

因为冻结余额如果和待处理订单对不上，排查起来会非常麻烦。

### 6. 新增后台对账查询接口

新增接口：

- `GET /admin/reconcile/account/{userId}`

当前支持：

- `userId`
- 可选 `chain`
- 可选 `tokenSymbol`

返回结果里会明确给出：

- 当前可用余额
- 当前冻结余额
- 当前总余额
- 已入账充值总额
- 已成功提现总额
- 待完成提现冻结总额
- 资产口径流水净额
- 最新流水快照
- 各类一致性判断结果
- 不一致原因汇总

这让项目第一次具备了：

`最小后台诊断视角`

这一步虽然还很轻，但已经明显开始往真实运维能力靠近。

### 7. 测试也同步补到了 Day21 语义

当前测试已经新增覆盖：

1. 手动补扫在未配置 RPC 时会跳过
2. 手动补扫会校验区块区间
3. 手动补扫会按请求区间执行，并在需要时裁剪到最新区块
4. 对账结果在一致场景下会返回全部通过
5. 对账结果在不一致场景下会返回明确失败原因
6. 控制器接口已经覆盖手动补扫和对账查询

到这里为止，项目测试总数已经推进到：

`30` 个

这意味着 Day21 不是只补了 README，而是代码和测试都已经真正落地。

## 五、Day21 最值得记住的几个工程判断

### 1. 补扫任务和正常扫描任务要分开

这是 Day21 非常关键的一条判断。

正常扫描任务的目标是：

`稳定按断点推进`

而补扫任务的目标是：

`人工回放历史区间`

这两个动作虽然都在“扫链”，但语义不同。

如果混在一起，最容易出问题的就是扫描断点。

所以 Day21 第一版选择：

`补扫可识别充值，但不更新正常扫描进度`

这是很合理的边界。

### 2. 对账不能只看“余额是不是 0”

很多系统初期做对账，会只看一个很粗的数字。

但资金系统至少应该分清：

1. 总资产对不对
2. 可用 / 冻结结构对不对
3. 当前冻结是不是都能映射到待处理订单

Day21 第一版虽然简单，但已经把这三层区分开了。

### 3. 冻结和解冻不等于总资产变化

这条非常值得记住。

冻结和解冻只是余额结构变化，不是总资产变化。

所以对账时如果直接把所有流水 `changeAmount` 累加，很容易把口径算错。

Day21 现在已经把这层区别显式做出来了，这对后面继续补账务能力会非常重要。

### 4. 对账接口第一版更像“诊断工具”而不是“自动修复器”

当前的接口只负责：

`告诉你哪里可能不一致`

它还不负责：

`自动修复`

这是一个很合理的阶段选择。

因为自动修复一旦做早了、做粗了，反而更危险。

## 七、当前版本还没有做什么

虽然 Day21 已经把补扫和对账补到了第一版，但还没有到生产级。

当前还没有完成的部分包括：

1. 自动定时对账任务
2. 对账结果落库与审计留痕
3. 链重组回退处理
4. 充值回滚与重新入账策略
5. 提现失败自动补偿任务
6. 长时间无回执订单巡检
7. 告警与监控指标
8. 更复杂的多链、多币种对账口径

所以当前最准确的表达应该是：

`我已经补了手动补扫和最小资产对账第一版，能说明我开始从主链路实现，进入到后台诊断和资金一致性视角，但还没做自动修复和生产级运维体系`

这个表述会很真实，也很专业。
