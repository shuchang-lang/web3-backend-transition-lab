# Day 17 - 提现申请与冻结第一版

今天进入 `Day 17`。

如果说前两天解决的是：

- `Day15`：怎么识别候选充值
- `Day16`：怎么把确认达标的充值正式入账

那么今天真正开始补的是钱包后端另一条同样重要的主线：

`怎么把用户的出金意图落成平台内部可控的提现订单`

这一步非常关键，因为一个钱包后端如果只有充值链路，没有提现申请和冻结能力，它就仍然只是“半条资金链路”。

---

## 一、Day17 的目标是什么

提现主链路如果一上来就做审核、广播、回执跟踪、失败回退，会非常容易把项目做散。

所以 Day17 最合理的落点不是：

`一次性把提现全做完`

而是：

`先把提现申请、余额冻结、订单落库这条最小出金起点做稳`

也就是说，这一天最重要的不是“链上发交易”，而是把下面这些问题立住：

1. 用户怎么发起提现申请
2. 平台怎么校验余额是否足够
3. 提现申请成功后怎么冻结余额
4. 如何保留提现订单状态承接层
5. 如何保留冻结流水，方便后续审核和回退

这和传统 Java 支付 / 账务系统的做法也非常一致：

`出金一定先有内部申请单，再有冻结，再有审核，再有真正执行`

---

## 二、为什么提现不能直接扣余额和发链上交易

很多人刚接触 Web3 钱包后端时，会把提现理解成：

`用户提交地址和金额 -> 平台直接广播一笔链上转账`

但真正的后端工程通常不会这样做。

因为提现天然带着更高的风险：

1. 是平台主动出金
2. 容易涉及风控和人工审核
3. 一旦广播错误，资金就可能不可逆转
4. 广播失败、节点异常、nonce 冲突都需要回退和补偿

所以更合理的顺序通常是：

1. 用户申请
2. 校验余额
3. 冻结资产
4. 落提现订单
5. 审核
6. 广播
7. 跟踪回执
8. 成功扣减或失败解冻

Day17 做的，就是先把前四步真正立起来。

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经新增了下面这些提现能力。

### 1. 增加提现订单实体和状态常量

新增了：

- `WithdrawOrder`
- `WithdrawStatusConstants`
- `WithdrawReviewStatusConstants`
- `WithdrawOrderMapper`

当前最小状态定义是：

- `status = PENDING_REVIEW`
- `reviewStatus = PENDING`

这代表项目已经开始明确区分：

- 订单主状态
- 审核状态

虽然现在还只是第一版，但这个结构对后续继续扩很重要。

后面你再加：

- 审核通过
- 审核拒绝
- 待广播
- 广播中
- 广播失败
- 链上成功

都会更自然。

### 2. 增加提现申请接口

新增接口：

- `POST /withdraw/apply`
- `GET /withdraw/list`
- `GET /withdraw/{requestNo}`

这意味着当前 demo 已经不只是“充币侧后端”，而是正式开始具备“出金币口”了。

对于 GitHub 展示和面试表达来说，这个变化很明显：

`从只会处理入金，推进到了开始处理出金起点`

### 3. 增加业务异常类型

新增了：

- `BusinessException`

并在 `ApiExceptionHandler` 里统一处理。

这一步看起来不大，但工程上很重要。

因为提现申请失败很多时候不是：

- 参数语法错误
- 资源不存在

而是典型的业务约束问题：

- 余额不足
- requestNo 重复
- 没有余额主表

这类场景如果没有单独的业务异常类型，接口层会很快变得混乱。

### 4. 余额主表支持冻结

`AccountBalance` 现在新增了：

- `freezeAvailable`

也就是：

`把 amount + fee 从 available_balance 转到 frozen_balance`

为什么这里先冻结 `amount + fee`？

因为当前最小版本先采用一个简化假设：

`提现资产和手续费资产是同一币种`

这对 demo 阶段是合理的。

真实生产系统里，ERC-20 提现常常还要单独处理 gas 币种，但那是后续再继续拆的内容。

### 5. 增加提现冻结流水

`AccountBill` 现在新增了：

- `WITHDRAW_FREEZE`

提现申请成功后，不仅更新余额主表，还会同步写一条账户流水。

这条流水记录了：

1. 哪个用户
2. 哪条链
3. 哪个币种
4. 哪笔提现申请
5. 本次冻结金额
6. 冻结后的可用余额
7. 冻结后的冻结余额

这层记录的价值非常高，因为它会直接决定：

- 后续审核失败怎么解冻
- 后续对账怎么追踪
- 出问题时怎么排查到底是哪笔申请导致余额变化

### 6. 提现申请支持 requestNo 幂等

当前 `WithdrawOrderAppService` 里已经开始处理：

- `requestNo`

也就是说，客户端重复提交同一个申请号时，系统不会简单地再次冻结余额。

这一步非常重要。

因为提现申请属于高风险操作，如果没有幂等保护，重复提交会很容易把冻结金额做大。

所以 Day17 虽然只是第一版，但已经开始体现出比较像样的资金系统意识。

## 四、当前提现主链路已经走到哪一步了

到 Day17 为止，当前最小出金主线可以概括成：

1. 用户提交提现地址、金额、手续费、requestNo
2. 系统校验余额主表是否存在
3. 校验可用余额是否覆盖 `amount + fee`
4. 将对应金额从可用余额转入冻结余额
5. 创建 `withdraw_order`
6. 状态先记为 `PENDING_REVIEW`
7. 同步写入 `account_bill`
8. 等待后续审核、广播和回执推进

这条链路虽然还没有“真正发链上交易”，但已经把出金起点最重要的内部约束做出来了。

更准确地说，你现在已经完成了：

`提现申请受理层`

## 五、Day17 最重要的工程判断

### 1. 出金一定先内部落单，再外部执行

充值更多是“接收链上世界的变化”。

提现则是“平台主动向链上发出动作”。

这两者在工程控制上完全不一样。

提现如果没有先落内部订单，很难处理：

- 审核
- 幂等
- 回退
- 重试
- 回执跟踪
- 审计

所以 Day17 先做提现订单层，是非常正确的顺序。

### 2. 冻结和扣减不能混成一件事

提现申请成功，不代表资金已经真正扣掉。

当前阶段应该先做的是：

- 冻结

而不是：

- 直接扣减

因为后面还可能出现：

- 审核拒绝
- 风控拦截
- 广播失败
- 节点异常

如果申请阶段就直接扣减，后续回退会更麻烦。

### 3. requestNo 是提现申请的第一层幂等保护

很多资金相关操作，如果没有客户端业务号或请求号，后面都很难做干净。

Day17 把 `requestNo` 放进提现申请里，本质上是在为：

- 重试
- 幂等
- 风控排查
- 客户端对账

打基础。

### 4. 流水一定要跟冻结动作一起落

如果冻结余额时只改主表、不落流水，后面你会很难回答：

- 为什么可用余额少了
- 哪一笔提现导致被冻结
- 冻结金额有没有重复

所以 Day17 把冻结流水一起补上，是很有价值的工程动作。

## 六、当前版本还没做什么

虽然提现申请已经能跑通，但这还只是提现链路的前半段。

当前还没有做的部分包括：

1. 审核通过 / 拒绝
2. 审核拒绝后的解冻
3. 广播链上交易
4. nonce 管理
5. 回执跟踪
6. 广播失败回退
7. 提现成功后的真正扣减

所以当前最准确的表达应该是：

`我已经完成提现申请与冻结第一版，具备了出金订单受理、余额冻结和冻结流水记录能力`

而不是：

`我已经完成完整提现系统`

这个边界一定要讲清楚。

- 账务流水

这些都是钱包后端和交易所后端非常看重的基础工程能力。

## 八、进入下一阶段前，要记住的 6 句话

1. Day16 解决的是“充值怎么正式入账”，Day17 解决的是“提现怎么安全受理”。
2. 提现申请成功不等于已经出金成功，中间至少还隔着审核和广播。
3. 冻结余额是提现链路里最重要的第一层资金控制动作。
4. `withdraw_order` 是后续审核、广播、回执跟踪的状态承接层。
5. `requestNo` 是提现申请防重、防重复冻结的第一层幂等保护。
6. 当前项目已经同时具备了入金主线和出金起点，这对 GitHub 展示价值很高。

## 九、Day18 最合理的推进方向是什么

在 Day17 之后，最自然的下一步是继续把提现主线往后推：

1. 审核通过 / 拒绝
2. 拒绝后的解冻
3. 广播前状态推进
4. 预留 nonce 与链上广播边界
5. 失败回退和补偿

如果只选最值得继续落地的一步，我会建议优先做：

`审核拒绝 + 解冻余额`

因为这样一来，提现链路就能形成一个最小闭环：

- 申请
- 冻结
- 审核
- 通过继续往下
- 拒绝则回退

这个闭环一旦成立，项目会更像真实后端。
