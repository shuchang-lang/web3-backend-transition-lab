# Day 15 - ERC-20 候选充值扫描第一版

今天进入 `Day 15`。

如果说 `Day13` 做的是“把项目骨架搭起来”，`Day14` 做的是“把充值监听前置的数据结构立住”，那么 `Day15` 真正开始把这条主链路推进到**能和真实链节点发生最小交互**的阶段。

这一天的关键词不是：

`把充值功能一次性做完`

而是：

`把 ERC-20 充值监听从“概念设计”推进到“可以识别候选充值”的第一版工程实现`

---

## 一、Day15 的目标到底是什么

对钱包后端来说，充值监听不是“查一笔交易”这么简单。

一个像样的后端链路，至少要回答下面几个问题：

1. 扫描从哪个区块开始
2. 一次扫多大窗口
3. 扫到哪一块算完成
4. 从日志里怎么识别 `Transfer event`
5. 哪些 `to address` 属于平台
6. 候选充值如何幂等落库
7. 下一轮怎么从断点继续跑

所以 Day15 的目标可以概括成一句话：

`先完成“识别候选充值 + 记录扫描断点”这两个最核心动作，先不急着做正式入账。`

这和传统 Java 后端的迁移思路非常一致：

- 先把“外部事件消费”跑通
- 再把“内部状态推进”做稳
- 最后补“账务落账”和“异常补偿”

---

## 二、今天实际落地了什么

当前 `practice/web3-wallet-backend-demo` 已经新增了下面几块真实能力：

### 1. 接入最小 `web3j` 网关

新增了 `Web3Gateway` 的真实实现边界：

- `Web3Gateway`
- `Web3jWeb3Gateway`
- `NoopWeb3Gateway`
- `Web3GatewayConfiguration`

这一步很重要，因为它意味着：

`Controller / Application Service / 持久层` 和 `链节点 SDK` 正式被隔离开了。

后面即使你要：

- 替换 RPC 提供商
- 增加多链支持
- 增加 mock / test stub
- 引入更复杂的日志消费策略

都不需要把业务层重写一遍。

这和你在 Java 后端里做第三方支付网关、短信网关、对象存储网关，本质上是同一种工程思路。

### 2. 增加链扫描配置

新增配置项：

- `WEB3_RPC_URL`
- `WEB3_DEPOSIT_TOKEN_CONTRACT`
- `WEB3_SCAN_START_BLOCK`
- `WEB3_SCAN_STEP`
- `WEB3_TOKEN_DECIMALS`

这代表扫描任务终于不再靠硬编码推进，而是具备了**最小可配置性**。

尤其是下面两个参数很关键：

- `scan-start-block`
  作用：第一次启动扫描时，从哪个区块开始追
- `scan-step`
  作用：每轮最多扫多少个区块，避免一次扫太大把节点压垮

这其实已经是一个标准后端任务的雏形了：

`有配置、有边界、有断点、有分批推进策略`

### 3. 扫描任务从“占位”升级到“真实识别”

`DepositScanTask` 现在不再只是初始化 `chain_scan_progress`。

它已经开始做下面这些事：

1. 初始化或读取扫描断点
2. 计算本轮扫描起止区块
3. 调用 `Web3Gateway` 读取指定 ERC-20 合约的 `Transfer event`
4. 把日志交给候选充值识别服务处理
5. 更新本轮扫描完成的区块断点

也就是说，这条主链路已经从：

`只有任务入口`

推进到了：

`有真实扫描编排能力`

这对 GitHub 展示和面试表达都很重要，因为这已经不是“伪代码式项目设计”了，而是有明确工程推进顺序的后端实现。

### 4. 增加候选充值识别与落库

新增了：

- `DepositCandidateAppService`
- `Erc20TransferLog`

这里完成的核心动作是：

`把链上 Transfer 日志和平台 wallet_address 做匹配，只把“打到平台地址”的日志写进 deposit_record`

注意这里写入的是：

`候选充值`

而不是：

`正式入账`

这是一个非常关键的工程判断。

因为在真实钱包后端里：

- 看到一笔链上 `Transfer`
- 和把用户余额加上去

中间通常还隔着：

- `confirmation（确认数）`
- `reorg（链重组）`
- 幂等校验
- 账务流水
- 状态流转

所以 Day15 先把这两个动作拆开，是完全正确的顺序。

### 5. 用唯一键兜住最小幂等

`deposit_record` 表上已经有：

- `UNIQUE KEY uk_deposit_record_tx_log (tx_hash, log_index)`

Day15 在代码层也配合了这个约束：

- 允许重复扫描同一窗口
- 如果同一条日志再次进入，就由唯一键兜底
- 重复数据直接跳过

这说明项目已经开始体现出 Web3 后端最关键的工程意识之一：

`链上监听一定不是“扫到一次就永远不会再扫”，重复扫描和幂等是默认前提`

## 三、Day15 这一步到底学到了什么

### 1. 充值监听的本质是“消费事件日志”

很多人刚开始会把充值理解成：

`我查一笔交易，看它是不是转给我`

但后端更常见的做法是：

`按区块范围消费 ERC-20 Transfer 日志，再判断 to 地址是不是平台地址`

因为这样更适合：

- 批量扫描
- 断点续跑
- 任务重试
- 多地址归属判断

这一步对从 Java 支付、账务、异步任务转 Web3 的人非常关键。

### 2. 候选充值和正式入账必须拆开

这是 Day15 最值得记住的一点。

看到链上日志，不代表就能立刻加余额。

至少在工程语义上，要先有一层：

- `PENDING_CONFIRM`

后面再推进成：

- `CONFIRMED`
- `CREDITED`

这和传统支付系统里“受理成功”不等于“清算入账”是同一个道理。

### 3. 区块扫描一定要有断点

`chain_scan_progress` 这张表看起来简单，但作用非常大。

没有它，你的扫描任务就会遇到这些问题：

- 应用重启后不知道从哪接着扫
- 任务失败后无法恢复
- 不知道是否漏块
- 也很难做补扫

所以 Day15 真正补上的，不只是“能扫日志”，而是：

`能像后端任务一样持续推进`

### 4. Web3 调用必须留在边界层

Day15 刻意没有把 `web3j` 直接写进 Controller 或具体业务方法里。

这不是为了“设计好看”，而是为了后面真正要演进时不崩。

后续你几乎一定会遇到：

- 节点切换
- 多链扩展
- 本地 mock
- 单元测试隔离
- 日志消费重构

如果现在就把 SDK 调用散在业务层，后面改一次会非常痛苦。

## 四、当前链路已经走到哪一步了

现在这条最小充值链路可以这样理解：

1. 后台手动触发 `POST /admin/deposit/scan/run`
2. 任务读取 `chain_scan_progress`
3. 按配置计算本轮扫描区块窗口
4. 通过 `web3j` 读取指定 ERC-20 合约的 `Transfer event`
5. 识别 `to address` 是否属于平台地址
6. 把命中的记录写入 `deposit_record`
7. 状态先记为 `PENDING_CONFIRM`
8. 扫描完成后推进区块断点

这已经比单纯的“查交易 hash”前进了一大步。

因为你现在做的是：

`链上事件消费型后端`

而不只是：

`链上接口调用 demo`

---

## 五、现在还没做的部分，不要误判成“已经完成充值”

虽然 Day15 已经能识别候选充值，但这还不能算“充值功能完成”。

当前仍然没做的部分包括：

1. 确认数推进
2. 正式入账
3. 余额主表更新
4. 账本流水写入
5. 链重组回滚处理
6. 定时调度与自动重试
7. 失败告警与监控

所以你现在最准确的表达不是：

`我已经完成了钱包充值功能`

而是：

`我已经完成 ERC-20 候选充值扫描第一版，具备了日志识别、地址归属判断、候选充值落库和扫描断点推进能力`

这个表达更专业，也更接近真实工程。

## 七、进入下一阶段前，要记住的 6 句话

1. Day15 的成果不是“充值完成”，而是“候选充值识别第一版完成”。
2. 看到链上 `Transfer event` 只是开始，正式入账还要经过确认数推进。
3. `deposit_record` 是候选充值与正式入账之间的状态承接层。
4. `chain_scan_progress` 是扫描任务能不能像后端任务一样持续运行的关键。
5. `Web3Gateway` 边界已经立住，后续再扩确认数、回执、广播都会更顺。
6. 这一步最重要的不是功能数量，而是工程顺序终于走对了。
