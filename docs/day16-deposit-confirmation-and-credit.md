# Day 16 - 确认数推进与正式入账第一版

今天进入 `Day 16`。

如果 `Day15` 解决的是：

`如何识别候选充值`

那么 `Day16` 解决的就是：

`什么时候才能把这笔充值真正记进平台账本`

这一步非常关键，因为钱包后端真正体现工程价值的地方，往往不在“我能扫到日志”，而在：

`我能不能安全地把链上事件推进成内部余额变更`

---

## 一、Day16 的核心目标是什么

从系统视角看，`Day15` 完成后，项目已经具备：

1. `wallet_address` 地址归属判断
2. `deposit_record` 候选充值落库
3. `chain_scan_progress` 区块断点推进
4. `web3j` 边界与日志读取能力

但这时还缺最关键的一步：

`用户余额并没有真的增加`

所以 Day16 的目标可以概括成一句话：

`把 deposit_record 从“待确认候选充值”推进到“达到确认阈值后正式入账”`

换成你熟悉的 Java 支付 / 账务语言，其实就是：

- Day15 更像“捕获外部支付成功信号”
- Day16 更像“把外部信号推进成内部账本落账”

---

## 二、为什么一定要加确认数推进

在传统支付系统里，很多人习惯了：

`收到回调 -> 校验成功 -> 更新订单 -> 入账`

但 Web3 充值不能这么简单处理。

原因在于：

1. 链上交易刚进块时，并不等于绝对稳定
2. 区块还可能发生 `reorg（链重组）`
3. 过早入账会把平台账实一致性做坏

所以对钱包后端来说，必须先有一层：

- `PENDING_CONFIRM`

等确认数达到阈值之后，才能推进到：

- `CREDITED`

这就是 Day16 的真正含义：

`把“看到了充值”推进成“可以安全记账”`

---

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经新增并打通了下面这几块能力。

### 1. 增加确认数阈值配置

新增配置：

- `WEB3_CONFIRMATIONS_THRESHOLD`

默认值：

- `6`

这意味着“正式入账门槛”终于不再是硬编码逻辑，而是一个可以调整的运行参数。

这一步很像传统后端里：

- 风控阈值
- 回调重试阈值
- 清算批次窗口

都应该走配置而不是写死在代码里。

### 2. 新增正式入账服务

新增了：

- `DepositSettlementAppService`

它负责做这几件事：

1. 查询所有 `PENDING_CONFIRM` 的充值记录
2. 根据 `latestBlock - depositBlock + 1` 计算当前确认数
3. 如果确认数不足，只刷新 `confirmations`
4. 如果确认数达到阈值，就正式入账
5. 更新 `account_balance`
6. 写入 `account_bill`
7. 把 `deposit_record` 状态推进为 `CREDITED`

这一步非常像传统账务系统里的“入账处理器”。

也就是说，到 Day16 为止，项目已经不再只是“链上监听 demo”，而开始真正具备：

`内部账本变更能力`

### 3. 新增账户流水实体

新增了：

- `AccountBill`
- `AccountBillMapper`
- `AccountBillBizTypeConstants`

为什么要补这层？

因为余额主表只能回答：

- 现在还剩多少

但它回答不了：

- 这笔钱是怎么变进来的
- 是哪一笔充值导致的
- 入账后余额是多少

所以正式入账时，必须落一条资金流水。

在当前最小版本里，流水已经记录了：

1. 用户
2. 链
3. 币种
4. 业务类型
5. 业务主键
6. 变动金额
7. 变动后可用余额
8. 变动后冻结余额
9. 备注

这对于后续扩展提现冻结、解冻、扣减、人工补账都会很有帮助。

### 4. 余额主表开始真正参与业务

Day13 和 Day14 阶段，`account_balance` 更多还是作为“主表骨架”存在。

Day16 开始，它已经真正被用到正式业务链路里：

- 充值确认达标
- 增加可用余额
- 持久化新余额

这一步代表项目已经跨过了一个很重要的门槛：

`从纯链上消费，进入账务落账`

### 5. 扫描任务升级为最小闭环

`DepositScanTask` 现在已经不只是：

- 扫描候选充值

而是进一步串起了：

1. 扫描新区块窗口
2. 识别候选充值
3. 刷新待确认充值的确认数
4. 达到阈值后正式入账
5. 更新扫描断点

所以当前任务入口已经可以看成：

`最小充值主链路执行器`

这一步对项目展示特别有价值，因为你现在能展示的不只是“监听逻辑”，而是“监听 + 入账”的完整后端闭环。

---

## 四、现在这条充值主链路长什么样

到 Day16 为止，当前最小钱包后端里的充值主链路已经可以概括成：

1. 给用户分配平台充值地址
2. 扫描 ERC-20 `Transfer event`
3. 判断 `to_address` 是否属于平台
4. 命中后写入 `deposit_record`
5. 状态先记为 `PENDING_CONFIRM`
6. 根据最新区块推进确认数
7. 达到阈值后更新 `account_balance`
8. 写入 `account_bill`
9. 把 `deposit_record` 改为 `CREDITED`

这条链路已经相当接近一个真实钱包后端的“充值最小闭环”了。

虽然还没处理链重组和复杂异常，但主线已经立住了。

## 五、这一步学到的最重要的工程判断

### 1. 候选充值和正式入账永远不是一回事

这是 Day16 最应该记住的工程判断。

链上事件只能证明：

`可能发生了一笔充值`

真正的账本更新，要等系统确认：

- 充值记录合法
- 地址归属正确
- 确认数达标
- 业务状态可推进

之后才能入账。

这也是 Web3 后端最容易区分“只会调链接口”和“理解资金后端”的地方。

### 2. 余额主表和资金流水必须一起出现

如果只有 `account_balance`，你只能看到余额结果。

如果只有 `account_bill`，你又看不到当前资产快照。

所以最小账务体系通常至少要有：

- 余额主表
- 流水明细

Day16 把这两层真正串起来了。

### 3. 状态推进必须带业务语义

Day16 当前最小状态流转虽然不复杂，但语义已经成立：

- `PENDING_CONFIRM`
- `CREDITED`

这意味着项目已经不是“存一条日志数据”，而是在表达：

`这笔充值目前处于什么业务阶段`

这对后续补：

- 补扫
- 对账
- 重试
- 人工排查

都非常重要。

### 4. 外部确认和内部账本必须解耦

链头最新区块变高，是“外部状态变化”。

余额增加，是“内部账本变化”。

Day16 的实现，本质上就是在做这两件事之间的可靠转换。

这一层转换，就是钱包后端的核心价值。

## 六、当前版本还没做什么

虽然 Day16 已经把正式入账做出来了，但仍然只是第一版。

当前还没有处理的部分包括：

1. `reorg（链重组）` 回退
2. 更细的入账状态机
3. 并发竞争下的更强幂等控制
4. 定时任务调度与自动重试
5. 充值补扫
6. 对账任务
7. 异常告警和监控指标

也就是说，现在最准确的表达应该是：

`我已经完成 ERC-20 充值从候选识别到正式入账的第一版闭环`

而不是：

`我已经完全做完了生产级充值系统`

这个表达更准确，也更专业。

## 八、进入 Day17 前，最该记住的 6 句话

1. Day15 解决的是“识别候选充值”，Day16 解决的是“安全地正式入账”。
2. `deposit_record` 是外部链上事件和内部账本变更之间的关键承接层。
3. `confirmations` 不是展示字段，而是正式入账的业务门槛。
4. `account_balance` 和 `account_bill` 必须配合出现，才能构成最小账务闭环。
5. 当前已经形成最小充值主链路，但还没有处理链重组和复杂补偿。
6. 这一步的真正价值，不是多写了几张表，而是开始具备了真正的钱包账务语义。
