# Day 24 - 提现回执超时巡检与异常订单治理第一版

今天进入 `Day24`。

如果说前面的提现链路已经解决了：

- 用户申请
- 余额冻结
- 审核通过
- 链上广播
- 回执同步

那么 Day24 要补上的，就是很多资金系统真正容易出问题的尾部环节：

`订单已经广播了，但长时间没有最终结果，接下来怎么办`

这一步非常关键。

因为很多项目不是主链路写不出来，
而是主链路一旦进入“半完成状态”，系统就不知道怎么继续治理。

对于 Web3 提现后端来说，这个半完成状态最典型的就是：

- `BROADCAST_SUBMITTED`

也就是：

`订单已经拿到 txHash，但迟迟没有最终回执`

---

## 一、为什么 Day24 必须补“长尾异常治理”

对于传统 Java 后端，你可能很熟悉下面这类场景：

- 调用下游成功发起请求
- 但下游迟迟不回调
- 本地状态停在“处理中”
- 这时必须靠巡检、超时补偿、人工处理机制继续推进

提现链路也是一样。

只不过在 Web3 里，这个“下游”不再是支付通道或第三方清算系统，
而是：

- 链节点
- mempool（待打包交易池）
- 链上出块和确认过程

所以提现订单一旦进入：

- `BROADCAST_SUBMITTED`

它其实只代表：

`我们已经把交易发出去了`

但并不代表：

`这笔提现已经真正成功或真正失败`

如果系统对这类订单没有后续治理能力，
就会很容易出现：

1. 冻结余额一直占着不释放
2. 订单长期挂在处理中无法解释
3. 运维不知道该继续等、重试，还是转人工
4. 面试时只能说“有回执同步任务”，却说不清超时场景怎么处理

Day24 做的，就是把这块补起来。

---

## 二、Day24 第一版的边界是什么

提现异常治理如果做深，会非常大。

你完全可以继续扩展：

- 不同链的超时阈值
- mempool 重发策略
- replace-by-fee（提高手续费替换交易）
- 独立异常工单表
- 运维认领机制
- 自动告警和通知

但 Day24 第一版我先只做最小闭环。

### 1. 只处理 `BROADCAST_SUBMITTED` 的订单

当前巡检只看：

- `status = BROADCAST_SUBMITTED`

因为这类订单的共同特征是：

- 已经通过审核
- 已经有链上交易哈希
- 还没有拿到最终成功 / 失败结论

这就是最需要做尾部治理的状态。

### 2. 超时判断先使用 `updatedAt`

当前第一版没有新增独立“广播提交时间”字段，
而是直接复用：

- `updatedAt`

来表达当前订单进入 `BROADCAST_SUBMITTED` 之后已经等待了多久。

这个边界是合理的，因为：

1. 订单被标记为 `BROADCAST_SUBMITTED` 时，`updatedAt` 会刷新
2. 如果回执一直没回来，后续状态不变，`updatedAt` 就可以近似代表“开始等待回执的时间”
3. 先不加新时间字段，可以让 Day24 第一版更轻、更容易验证

### 3. 超时后一定先重查一次回执

这是 Day24 很重要的一个判断。

即使订单已经超过等待阈值，
当前也不会直接把它打回待广播，
而是先做一次：

- `re-check receipt（重查回执）`

原因很简单：

`超时` 不等于 `失败`

它也可能只是：

- 节点视角延迟
- 网络抖动
- 上一轮任务没及时扫到

所以 Day24 第一版在超时后会先问链：

`这笔 txHash 现在到底有没有结果`

### 4. 仍然没结果时，再区分三类动作

当前第一版把长时间无回执订单分成三类：

1. 继续等待
2. 可重试
3. 待人工处理

也就是说，Day24 不是简单地“超时就失败”，
而是第一次把：

`异常订单治理策略`

明确地写进了状态机。

## 三、Day24 今天到底实现了什么

当前 `practice/web3-wallet-backend-demo` 已经补了下面几块核心能力。

### 1. 提现订单新增最小治理字段 `receiptCheckRetryCount`

`WithdrawOrder` 新增：

- `receiptCheckRetryCount`

这个字段表示：

`这笔订单因为回执长时间未返回，被巡检任务打回待广播重试过多少次`

为什么 Day24 要补这个字段？

因为如果没有最小重试计数，
系统就很难回答一个关键问题：

`这笔订单到底是第一次超时，还是已经超时很多轮了`

而这正是“继续自动重试”还是“转人工处理”的分界线。

### 2. 新增人工处理状态 `MANUAL_HANDLE_REQUIRED`

`WithdrawStatusConstants` 新增：

- `MANUAL_HANDLE_REQUIRED`

这一步的意义非常大。

因为 Day24 开始，提现订单状态机已经不只是：

- `PENDING_REVIEW`
- `PENDING_BROADCAST`
- `BROADCAST_SUBMITTED`
- `SUCCESS`
- `FAILED`

它第一次开始表达：

`系统已经知道自己不能再自动推进，必须交给人工介入`

这是很典型的后端治理能力。

### 3. 提现订单新增两个领域动作

`WithdrawOrder` 新增：

- `markReceiptTimeoutRetryable(...)`
- `markManualHandleRequired(...)`

它们分别表示：

1. 回执超时，但还可以再打一轮待广播重试
2. 回执超时且已达到自动治理边界，转人工处理

这和你熟悉的 Java 资金系统建模非常像：

- 自动重试
- 达到上限
- 转人工单

只是这里触发原因来自链上回执迟迟不返回。

### 4. `WalletWeb3Properties` 增加 Day24 两个治理参数

新增配置：

- `withdraw-receipt-timeout-minutes`
- `withdraw-receipt-max-timeout-retry-count`

默认值分别是：

- `10` 分钟
- `2` 次

这意味着当前第一版策略是：

1. 一笔已广播提现等待超过 10 分钟
2. 巡检任务会先重查回执
3. 如果仍然没有结果，最多允许打回待广播重试 2 次
4. 超过这个次数，就进入 `MANUAL_HANDLE_REQUIRED`

这两个参数很适合后面继续演进成：

- 链级别配置
- 热钱包级别配置
- 任务中心统一配置

### 5. `WithdrawExecutionAppService` 新增超时巡检能力

当前新增：

- `inspectTimeoutSubmittedOrders()`

这是 Day24 的核心逻辑。

它的处理顺序是：

1. 查询所有 `BROADCAST_SUBMITTED` 的订单
2. 用 `updatedAt` 判断是否超过回执等待阈值
3. 未超时则继续等待
4. 已超时则先重查链上回执
5. 如果回执已经出现：
   - 成功则直接走成功结算
   - 失败则直接走失败回退
6. 如果仍然没有回执：
   - 重试次数未到上限，则打回 `PENDING_BROADCAST`
   - 重试次数已到上限，则转 `MANUAL_HANDLE_REQUIRED`

注意这里有一个很重要的工程判断：

`超时巡检不是重复造一套结算逻辑，而是复用已有成功 / 失败结算能力`

这意味着当前项目的提现链路开始有了比较清晰的层次：

- 主链路负责广播
- 回执同步负责常规推进
- 超时巡检负责长尾异常治理

### 6. 新增独立任务入口 `WithdrawTimeoutCheckTask`

新增：

- `WithdrawTimeoutCheckTask`

以及任务名：

- `withdraw_receipt_timeout_check`

这个任务返回的数据会明确区分：

- `processedCount`
- `continueWaitingCount`
- `resolvedCount`
- `retryableCount`
- `manualHandleCount`

也就是说，Day24 第一版不是只说“我巡检过了”，
而是开始告诉系统和运维：

`这轮巡检到底把订单分到了哪几类`

### 7. 新增后台接口

新增接口：

- `POST /admin/withdraw/timeout/check/run`

这一步让当前项目第一次具备了一个比较像真实后台的治理动作：

`手动触发一轮已广播提现订单超时巡检`

这对于 GitHub 展示和面试表达都很有帮助，
因为你可以很清楚地说明：

`这个系统不仅能发起提现，还能治理发出去以后迟迟没结果的订单`

### 8. 对外订单响应同步补充治理字段

`WithdrawOrderResponse` 现在也会返回：

- `receiptCheckRetryCount`

这意味着不只是内部状态机知道一笔订单重试过几次，
对外查询订单时，系统也能把这个治理痕迹展示出来。

这会明显提升后台排障和项目表达的完整度。

### 9. 测试也同步补到了 Day24 语义

当前测试已经新增并覆盖：

1. 未超时订单会继续等待，不误处理
2. 超时但仍可重试的订单，会回退到 `PENDING_BROADCAST`
3. 达到最大超时重试次数的订单，会转 `MANUAL_HANDLE_REQUIRED`
4. 超时后重查回执，如果发现其实已经成功，会直接完成结算
5. 未配置 RPC 时，超时巡检任务会跳过
6. 控制器可以正常触发 `POST /admin/withdraw/timeout/check/run`

到这里为止，当前项目测试总数已经推进到：

`46`

这说明 Day24 不是“只写了点说明文档”，
而是真正把代码、测试和接口一起落了下来。

## 四、Day24 最重要的工程判断

### 1. 已广播不等于已完成

这是提现系统里很重要的一句话。

`BROADCAST_SUBMITTED`

只能说明：

`我们已经把交易发出去了`

但它并不自动等于：

- 成功
- 失败
- 结束

所以 Day24 开始，系统第一次明确承认：

`已广播订单本身也需要治理`

### 2. 超时不是失败，而是一个新的治理信号

这是 Day24 非常核心的边界控制。

很多系统会犯一个错误：

`看到超时就直接判失败`

但链上世界不是这样。

一笔交易超时，可能意味着：

- 还没被打包
- 节点没查到
- 上一轮同步没扫到
- 交易池里卡住了

所以超时更准确的含义是：

`这笔订单需要进入更高优先级的治理流程`

而不是立刻直接失败。

### 3. 自动治理必须有上限

Day24 新增 `receiptCheckRetryCount` 和 `MANUAL_HANDLE_REQUIRED`，
本质上是在回答一个很真实的问题：

`系统打算自动重试到什么程度为止`

这和很多 Java 后端里的任务治理原则完全一致：

- 自动处理可以有
- 但不能无限自动处理
- 一旦达到边界，要明确转人工

### 4. 先重查回执，再决定要不要重试

这是一个非常值得在面试里讲的细节。

因为它体现了你不是简单做了个：

`超时扫描 + 改状态`

而是在超时后先做了一次：

`事实确认`

这就是比较成熟的治理思路。

### 5. 尾部异常治理和主流程解耦

Day24 没有把所有超时逻辑硬塞进：

- 广播任务
- 回执同步任务

而是拆出独立的：

- 超时巡检任务

这种拆法很好，因为后面你如果继续扩展：

- 定时触发
- 告警
- 人工工单

都会更清晰。

## 五、Day24 之后，提现链路发生了什么变化

到 Day24 为止，提现主链路已经从：

`申请 -> 冻结 -> 审核 -> 广播 -> 回执同步 -> 成功/失败`

扩展成：

1. 用户发起提现申请
2. 冻结 `amount + fee`
3. 审核通过进入 `PENDING_BROADCAST`
4. 广播成功进入 `BROADCAST_SUBMITTED`
5. 常规回执同步任务推进成功 / 失败
6. 如果长时间没有最终回执，进入超时巡检
7. 巡检时先重查回执
8. 有结果则直接结算
9. 无结果则区分：
   - 继续等待
   - 转回待广播重试
   - 转人工处理

这意味着当前项目已经不只是“会发起提现”，
而是开始具备：

`治理已发起但迟迟没有结果的出金订单`

的能力。

这对钱包后端、交易所后端都非常关键。

## 六、当前版本还没有做什么

虽然 Day24 已经完成了第一版超时治理，但它依然只是最小版本。

当前还没有做：

1. 独立异常订单表或工单系统
2. 更细粒度的超时原因分类
3. 不同链 / 币种 / 热钱包差异化阈值
4. 更激进的替换交易或手续费提升策略
5. 自动告警、通知和人工认领
6. 针对 `nonce` 堵塞的串行保护

所以目前最准确的表达应该是：

`我已经实现了提现回执超时巡检与异常订单治理第一版，系统能识别长时间无回执订单、重查回执、回退待广播重试并在达到上限后转人工处理，但还没有进入更复杂的费用替换和工单治理阶段`

这个表达会比“我已经完全解决提现异常订单问题”更真实、更专业。

## 七、从 GitHub 展示和面试角度，Day24 的价值是什么

Day24 的价值非常高，因为它开始明显体现出：

`这个项目会治理尾部异常，而不是只会走 happy path`

对外展示时，Day24 最能说明的几件事是：

### 1. 你知道资金系统最难的不是建主流程，而是收尾

这句话非常适合放进面试表达里。

### 2. 你会把异常治理写进状态机和任务系统

不是靠人工口头说“发现异常再处理”，
而是真正落成：

- 状态
- 重试计数
- 任务入口
- 巡检逻辑

### 3. 你理解 Web3 后端和普通后端的共同点与差异点

共同点在于：

- 都需要超时治理
- 都需要补偿与转人工

差异点在于：

- 这里的“下游确认”来自链上回执
- 这里的“处理中”状态和 `nonce`、mempool、链上出块有关

这类表达会非常贴近 `钱包后端 / 交易所后端` 岗位的面试关注点。

## 八、Day25 最合理的推进方向是什么

Day24 做完以后，最自然的下一步就是：

`Day25：nonce 锁与串行广播第一版`

因为现在你已经补了：

- 充值异常治理
- 提现尾部异常治理

接下来最值得继续补的，就是提现广播阶段另一个典型的 Web3 风险：

`多个任务并发竞争同一个热钱包 nonce`

所以 Day25 很适合继续做：

1. 串行广播
2. 本地锁或数据库锁第一版
3. 避免并发任务把同一热钱包的 nonce 用乱

这样项目会继续从“会做提现治理”推进到“会做提现执行稳定性控制”。

## 阶段结论

Day24 的本质，不只是多了一个后台接口，也不只是多了一个状态和计数字段。

它真正补上的，是：

`系统开始具备对已广播提现订单做长尾异常治理的能力`

更准确地说，到今天为止，这个项目主线已经形成了：

`充值扫描 -> 确认入账 -> reorg 风险识别 -> 充值补偿 -> 提现申请 -> 冻结 -> 审核 -> 广播 -> 回执同步 -> 提现回执超时巡检`

这条主线已经越来越像一个真正的资金后端学习项目：

- 不只会主流程
- 会处理链上异常
- 会做状态机治理
- 会把自动处理边界和人工处理边界表达清楚

这对 GitHub 展示和求职表达，都会是非常加分的一步。
