# Day 13 - Project Kickoff

今天准备进入 `Day 13`。

但在真正开始写 Spring Boot 项目之前，先做一件很重要的事：

`把 Day01 到 Day12 学到的内容重新收束一遍，明确自己现在已经具备哪些能力，以及为什么 Day13 应该从“最小钱包后端骨架”开始。`

这一步不是重复复习，而是把前面的知识压缩成一套可以指导实现的工程认知。

---

## 一、先回答一个问题：为什么 Day13 之前要再总结一次

因为从 Day01 到 Day12，你已经不只是“学过一些 Web3 概念”了。

你实际上已经完成了 4 个层次的准备：

1. 链上基础认知
2. 合约与工程化基础
3. Java 接链与事件消费基础
4. 钱包后端业务与系统设计基础

这意味着 Day13 之后的工作重点会发生变化：

- 之前更偏“理解”
- 从 Day13 开始更偏“落地”

也就是说，接下来不再是继续零散补知识点，而是要把这些知识真正装进一个能跑起来的 Spring Boot 项目里。

---

## 二、Day01 到 Day12 到底学会了什么

可以把前 12 天的内容分成四个阶段来看。

### 第一阶段：你已经理解了链上世界最基本的运行单位

对应：

- Day01：账户与钱包
- Day02：交易、Gas、Nonce
- Day03：EVM、存储与日志

这一阶段最重要的收获，不是记住几个术语，而是建立了一个最基本的链上执行模型：

- `EOA（外部账户）` 是由私钥控制的账户
- `contract account（合约账户）` 是部署在链上的程序账户
- 一切状态变化都要通过 `transaction（交易）` 触发
- 交易执行要消耗 `gas（链上执行成本）`
- 同一个地址发交易要依赖 `nonce（交易序号）` 保证顺序
- 链上执行结果会沉淀成 `receipt（交易回执）` 和 `event log（事件日志）`

如果换成 Java 后端的语言，这一阶段相当于你已经搞清楚了：

- 系统里的核心对象是谁
- 请求是怎么提交的
- 状态是怎么变化的
- 结果是怎么返回和留痕的

这一步非常关键，因为后面的充值监听、提现跟踪、账本入账，本质上都建立在这套执行模型之上。

---

### 第二阶段：你已经理解了合约交互和工程化工具链

对应：

- Day04：Solidity 基础
- Day05：ERC-20、ABI、事件
- Day06：Hardhat 工程化流程

这一阶段最重要的收获，是你不再把链上交互理解成“黑盒调用”。

你已经知道：

- `Solidity（智能合约语言）` 合约里有哪些最核心的结构
- `ERC-20（同质化代币标准）` 为什么是钱包、交易所、支付场景最常见的资产模型
- `ABI（合约接口描述）` 为什么是链下程序调用合约的前提
- `Transfer event（转账事件）` 为什么是充值监听最关键的数据来源
- `Hardhat（以太坊开发框架）` 为什么适合拿来做本地编译、测试、部署和联调

这意味着你已经不只是会“读链”，还开始理解“链上的资产动作是怎么被定义和暴露出来的”。

这对 Day13 很重要，因为你后面写钱包后端时会不断碰到这些问题：

- 为什么 ERC-20 充值不能只看交易里的 `value`
- 为什么需要用日志来识别实际入金
- 为什么要把合约地址、事件签名、字段解码这些能力做成可复用基础设施

---

### 第三阶段：你已经建立了 Java 视角的接链能力

对应：

- Day07：Java + web3j 读链
- Day08：合约调用与日志解码

这一阶段的意义，在于你已经把 Web3 概念翻译成了 Java 后端能真正操作的东西。

你已经知道：

- 怎么通过 `RPC（节点远程调用）` 连接链节点
- 怎么查询区块、交易、余额和回执
- 怎么区分 `eth_call（只读调用）` 和发送交易
- 怎么读取和解析日志
- 怎么把链上的结构化结果变成 Java 代码里的对象和业务数据

从职业转型角度看，这是一个很关键的分界点。

因为很多人学 Web3 时会停留在：

- 看概念
- 跑前端钱包 demo
- 看合约例子

但对一个想转 `wallet backend（钱包后端）`、`exchange backend（交易所后端）`、`chain-data/indexer（链上数据索引服务）` 的 Java 后端来说，真正有价值的是：

`你已经能站在 Java 服务的视角，去读取链、理解链、消费链上的结果。`

---

### 第四阶段：你已经完成了钱包后端的核心业务建模

对应：

- Day09：充值监听链路
- Day10：提现链路
- Day11：钱包后端架构
- Day12：最小项目设计

这是前 12 天里最重要的一段，因为它把“链上认知”真正推进成了“后端系统设计”。

到这里，你已经知道：

- 充值不是扫到交易就立刻入账，而是要先识别、再等待 `confirmation（确认数）`
- 提现不是调用一个接口就结束，而是要经过申请、冻结、审核、广播、回执跟踪和最终结转
- `chain state（链上状态）` 和 `internal ledger（内部账本）` 不是一回事
- 钱包后端真正的核心是把链上变化稳定映射成平台内部账务
- 账本、流水、幂等、状态机、补偿、审计这些能力不是附属能力，而是系统底座

更重要的是，你已经把这个系统设计到了足够细的程度：

- 有模块划分
- 有数据表
- 有状态流转
- 有 API 清单
- 有第一版范围边界
- 有后续实现顺序

这意味着 Day13 并不是从 0 开始做项目，而是从一个已经明确过边界和路线的蓝图开始落地。

---

## 三、如果把前 12 天浓缩成 4 句话

进入 Day13 前，最值得真正带走的其实是下面这 4 句话：

1. Web3 后端不是“会发一笔链上交易”，而是“能稳定消费链上结果并把它变成后端业务状态”。
2. 钱包后端的核心不是单独处理充值或提现，而是围绕统一账本维护账实一致。
3. Java 后端转 Web3 后端最大的优势，不是会某个新框架，而是懂资金系统、状态机、幂等、补偿和审计。
4. 从 Day13 开始，重点不再是继续补更多概念，而是把已有认知装进一个可运行项目。

## 四、为什么 Day13 要从 Spring Boot 项目骨架开始

很多人在这个阶段容易有一个冲动：

`直接先写充值监听，或者直接先写一个提现接口。`

但如果这样做，很容易把项目做成一堆孤立 demo，而不是一个后续能持续生长的钱包后端。

所以 Day13 最合理的起点，不是马上写复杂链路，而是先搭一个最小可扩展的 Spring Boot 项目骨架。

原因有 4 个：

### 1. 你已经有足够的设计输入了

前面 12 天已经把这些东西想清楚了：

- 模块有哪些
- 表有哪些
- 状态有哪些
- 接口有哪些
- 链路怎么串

现在缺的不是继续想，而是把这些设计装进项目结构里。

### 2. 骨架决定后续实现质量

如果 Day13 没把项目基本结构搭好，后面很容易出现：

- 链交互代码散落在各处
- 账务更新逻辑耦合在监听任务里
- 状态流转硬编码
- API、任务、持久化边界不清晰

一开始就把边界摆正，后面加充值监听和提现流程会轻松很多。

### 3. Day13 的目标应该是“让项目站起来”

第一天进入实现阶段，最重要的不是功能做多，而是先把这些基础立住：

- Spring Boot 工程能启动
- 配置结构明确
- 持久化方案明确
- 基础表可以建起来
- 地址和余额两个简单对象可以先跑通

只要这一步完成，项目就从“设计文档”变成“工程项目”了。

### 4. 这也最符合 GitHub 展示逻辑

一个适合展示的仓库，不应该只有文档，还应该能让别人看到：

- 项目结构是怎么落地的
- 第一批领域对象是什么
- 你打算怎么把设计推进成代码

Day13 做骨架，恰好就是这个转折点。

## 五、Day13 到底要做什么

建议把 Day13 的目标定义成：

`搭建一个最小可运行的 Spring Boot 钱包后端骨架，为后续地址管理、余额查询、充值监听和提现流程提供统一工程基础。`

这一天不要追求把充值和提现都做完，而是把最小骨架搭稳。

### Day13 建议完成的内容

#### 1. 新建 Spring Boot 项目

至少明确：

- JDK 版本
- Maven 结构
- 包结构
- 配置文件

#### 2. 定义最小分层

建议先有这些基本层：

- `controller`
- `service` 或 `application`
- `repository` / `mapper`
- `domain` / `model`
- `infrastructure`
- `task`

#### 3. 接入数据库

建议先接 MySQL，把第一版核心表准备好：

- `wallet_address`
- `account_balance`
- `account_bill`
- `deposit_record`
- `withdraw_order`

Day13 可以先不把所有表都完全用起来，但表结构最好先定下来。

#### 4. 先跑通两个最简单的能力

建议优先做：

- 地址查询 / 分配
- 余额查询

为什么是这两个？

因为它们最适合作为项目骨架验收点：

- 足够简单
- 涉及 controller、service、repository、db 全链路
- 不会马上引入复杂链交互
- 又和后续充值、提现直接相关

#### 5. 预留链交互与任务入口

即使 Day13 还不真正实现充值监听，也建议先把这些入口预留好：

- `web3 client`
- `scheduler task`
- `deposit service`
- `withdraw service`

这样 Day14 之后往里填功能时，结构不会乱。

## 六、Day13 为什么先做“地址管理 + 余额查询”

这一点非常重要。

很多人会觉得这两个功能太简单，不像 Web3。

但其实它们恰恰是最适合做第一步的：

### 1. 地址管理是充值链路的前置条件

没有地址管理，后面你根本无法判断：

- 某个 `to address` 是不是平台地址
- 这笔链上转账应该归属给哪个用户

也就是说，充值监听不是从扫链开始，而是从地址映射开始。

### 2. 余额查询是账本体系的最小对外窗口

后面无论充值成功还是提现冻结，最终都要落到余额模型上。

所以先把：

- `account_balance`
- 查询接口
- 基本返回结构

这些东西跑通，后面加账务动作会更顺。

### 3. 它们最适合作为工程骨架验证

这两个功能能帮你验证：

- 分层是否合理
- 实体模型是否清楚
- 持久化是否稳定
- API 风格是否统一

这其实就是 Day13 最应该做的事。

## 七、前面学的知识，具体会怎样支撑 Day13

这部分最值得你记下来，因为它体现了“知识没有白学”。

### Day01-Day03 支撑什么

支撑你正确设计这些基础字段和对象：

- 地址
- 交易哈希
- 区块号
- nonce
- 日志索引
- 合约地址

也支撑你知道哪些链上概念必须在数据库里留出来。

### Day04-Day06 支撑什么

支撑你知道后面链交互模块为什么必须围绕：

- 合约地址
- ABI
- 事件签名
- 测试链部署

这些能力来设计。

### Day07-Day08 支撑什么

支撑你后面在基础设施层接入：

- `web3j client`
- 查询区块和回执的接口
- 日志解析器

也让你知道后面 `deposit task` 不是凭空写出来的，而是建立在真实链交互能力之上。

### Day09-Day12 支撑什么

支撑你在 Day13 做对这些工程决策：

- 为什么项目一定要有账本对象
- 为什么要有冻结余额
- 为什么 `deposit_record` 和 `withdraw_order` 必须独立建模
- 为什么定时任务和状态机以后一定会出现
- 为什么签名和广播能力不应该散落在业务代码里

所以 Day13 不是另起炉灶，而是前 12 天的自然延伸。

## 八、Day13 不该做什么

进入实现阶段后，很容易出现“想一口气做完”的问题。

Day13 建议明确不要做这些事：

- 不要一开始就做多链
- 不要一开始就做复杂风控
- 不要一开始就做热冷钱包归集
- 不要一开始就做完整提现广播闭环
- 不要一开始就把所有状态机一次写完
- 不要为了“像真实项目”过早引入过多中间件

Day13 最重要的是：

`把项目骨架、最小对象、最小接口和最小数据流先建立起来。`
