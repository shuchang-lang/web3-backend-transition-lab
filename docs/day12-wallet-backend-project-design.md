## 二、这个最小项目的目标是什么

建议把 Day12 对应的项目目标定义成：

`设计并逐步实现一个面向 EVM 单链、单 ERC-20 资产场景的最小钱包后端 demo，覆盖充值地址管理、充值监听、确认数处理、提现申请、审核与广播、账本与流水、补偿与重查等核心能力。`

这个定义有几个好处：

### 1. 范围足够聚焦

第一版不要一开始就做：

*   多链支持
*   多币种路由
*   热冷钱包归集
*   MPC / HSM（硬件安全模块）
*   托管体系
*   复杂风控引擎
*   多租户账户体系

这些当然重要，但如果第一版全做，工程会迅速失控。

### 2. 足够体现 Web3 后端价值

虽然是最小版本，但它已经能覆盖钱包后端最关键的工程问题：

*   如何稳定消费链上 `event log（事件日志）`
*   如何处理 `confirmation（确认数）`
*   如何避免重复入账
*   如何做提现冻结和状态流转
*   如何把链上结果沉淀到内部账本
*   如何做失败重查和补偿

### 3. 足够适合 GitHub 展示

一个用于展示的项目，不一定要“大而全”，但一定要：

*   场景真实
*   边界清晰
*   结构完整
*   叙事连贯
*   能看出工程判断

## 三、这个项目建议覆盖哪些能力

建议第一版明确覆盖以下功能：

### 用户侧能力

1.  查询或分配充值地址
2.  查询充值记录
3.  提交提现申请
4.  查询提现记录
5.  查询账户余额和冻结余额

### 后台侧能力

1.  扫描区块并识别 ERC-20 充值
2.  按确认数推进充值状态
3.  审核提现申请
4.  广播提现交易并保存 `txHash（交易哈希）`
5.  跟踪提现回执和确认状态
6.  对异常充值或异常提现执行重查

### 系统底座能力

1.  内部账本
2.  资金流水
3.  状态机
4.  幂等控制
5.  断点续跑
6.  定时补偿

***

## 四、第一版明确不做什么

为了保证项目可交付，第一版建议明确不做：

*   原生币充值与提现和 ERC-20 混合在一起
*   多链统一抽象
*   归集、扫尾、手续费自动补充
*   用户级复杂风控规则
*   多签和企业级密钥托管
*   实时消息通知
*   复杂后台运营系统

一句话说，第一版的重点不是业务面铺开，而是把一条资金链路做完整。

***

## 五、项目的最小业务假设

为了让设计更容易落地，建议先约定几个最小业务前提：

1.  只支持一条 `EVM` 链
2.  只支持一个 ERC-20 token 合约
3.  每个用户分配一个平台维护的充值地址
4.  充值通过监听 `Transfer event（转账事件）` 识别
5.  提现由平台热钱包统一广播
6.  账务模型只维护：
    *   `available_balance（可用余额）`
    *   `frozen_balance（冻结余额）`
7.  提现必须经过审核
8.  充值与提现都要走统一账本流水

这样做的好处是：复杂度可控，但主干能力是完整的。

## 六、可以把这个项目理解成哪几层

如果站在 Java 后端的视角，这个项目可以理解成 5 层：

### 1. API 层

负责对外提供接口，例如：

*   地址查询
*   余额查询
*   提现申请
*   充值记录查询
*   提现记录查询

### 2. 业务层

负责业务编排，例如：

*   地址分配
*   充值识别
*   提现申请与审核
*   余额冻结与解冻
*   入账与扣账

### 3. 链交互层

负责和链直接交互，例如：

*   区块扫描
*   日志解析
*   交易构造
*   签名调用
*   广播交易
*   查询回执

### 4. 账务层

负责内部资金状态管理，例如：

*   用户余额
*   冻结余额
*   资金流水
*   账务幂等
*   状态流转

### 5. 支撑层

负责工程稳定性，例如：

*   MySQL
*   Redis
*   定时任务
*   分布式锁
*   审计日志
*   监控告警

你会发现，这套结构对于 Java 后端非常友好，因为本质上仍然是：

`API + 业务服务 + 基础设施 + 数据库 + 异步任务`

真正变化的只是外部事件源从“支付渠道”变成了“区块链”。

## 七、建议的模块划分

### 1. 地址管理模块

职责：

*   为用户分配充值地址
*   维护地址和用户映射关系
*   按链和币种管理地址状态

为什么需要它：

因为充值识别不是看到任意转账都算，而是要判断“是否打到了平台已登记地址”。

### 2. 区块同步模块

职责：

*   持续扫描新区块
*   保存扫描进度
*   支持断点续跑
*   控制扫描窗口范围

为什么需要它：

这是所有充值识别的入口，没有稳定的区块扫描，就没有稳定的充值监听。

### 3. 日志解析模块

职责：

*   过滤目标 token 合约
*   过滤 `Transfer event`
*   解出 `from / to / amount`
*   结合地址表判断是否命中平台充值地址

为什么需要它：

ERC-20 充值真正可靠的数据来源，通常不是交易表面字段，而是 `receipt + log`。

### 4. 充值处理模块

职责：

*   生成候选充值记录
*   推进确认数
*   达标后执行正式入账
*   处理链重查和异常状态修复

为什么需要它：

监听到链上事件只是开始，真正的业务结果是“是否可以安全入账”。

### 5. 提现申请模块

职责：

*   接收提现请求
*   校验参数和余额
*   生成提现单
*   冻结可用余额

为什么需要它：

提现不是直接发交易，而是先形成一笔平台内部待处理资金请求。

### 6. 审核与广播模块

职责：

*   审核提现单
*   构造链上交易
*   申请签名
*   广播交易
*   保存 `nonce` 和 `txHash`

为什么需要它：

提现的核心不是“有个接口”，而是把审核、签名和广播边界清晰地拆开。

### 7. 回执跟踪模块

职责：

*   跟踪已广播提现交易
*   查询是否打包
*   查询是否执行成功
*   查询确认数是否达标

为什么需要它：

拿到 `txHash` 不等于提现成功，最终成功判断要以链上执行结果和确认数为准。

### 8. 账本模块

职责：

*   管理可用余额和冻结余额
*   记录每一笔资金流水
*   保证账务更新和流水写入原子性
*   为充值和提现提供统一资金底座

为什么需要它：

钱包后端真正的核心，不是监听器，而是内部账本。

### 9. 对账与补偿模块

职责：

*   重查异常充值
*   重查异常提现
*   检测状态卡顿
*   定时补偿失败任务

为什么需要它：

链上系统天然存在网络波动、节点延迟、确认不足、状态卡单等问题，补偿能力必须提前设计。

## 九、充值链路应该怎么设计

充值主链路建议拆成 8 步：

1.  用户获取充值地址
2.  用户向该地址发起 ERC-20 转账
3.  系统扫描新区块并读取目标合约日志
4.  解析出 `to` 地址并命中平台地址表
5.  生成一条待确认充值记录
6.  定时任务更新该记录的确认数
7.  确认数达标后执行正式入账
8.  写余额和流水，并把充值状态推进为成功

### 关键设计点 1：充值不能一看到就入账

因为监听到的只是“候选入金事件”，还不能直接等同于“业务已到账”。

后端至少要确认：

*   交易确实执行成功
*   事件日志解析正确
*   `confirmation（确认数）` 达标
*   没有明显的 `reorg（链重组）` 风险

所以更稳妥的做法是：

*   先写 `deposit_record`
*   状态记为 `PENDING_CONFIRM`
*   确认数达标后再执行 `CREDITED`

### 关键设计点 2：充值幂等的核心键是什么

ERC-20 充值通常建议使用：

*   `tx_hash + log_index`

作为唯一键。

原因是同一笔交易里可能出现多个事件日志，仅用 `tx_hash` 不一定足够区分。

### 关键设计点 3：正式入账必须和账本流水放在一个事务里

充值确认达标后，系统至少要同时做三件事：

1.  更新充值记录状态
2.  增加 `account_balance.available_balance`
3.  插入一条 `account_bill`

这三件事应该在同一个数据库事务中完成，否则容易出现：

*   充值状态成功了，但余额没加
*   余额加了，但流水没记
*   流水有了，但状态没推进

## 十、提现链路应该怎么设计

提现主链路建议拆成 10 步：

1.  用户提交提现申请
2.  系统校验地址、币种、金额和余额
3.  生成提现单
4.  把可用余额转为冻结余额
5.  提现单进入待审核状态
6.  审核通过后进入待广播状态
7.  构造交易、申请签名、广播交易
8.  保存 `txHash`、`nonce` 和广播时间
9.  定时跟踪回执和确认数
10. 成功则扣减冻结，失败则解冻回退

### 关键设计点 1：提现申请不是直接打款

提现本质上是一笔资金请求，不是一条链上交易本身。

所以第一步应该是：

*   生成业务提现单
*   冻结余额
*   等审核和广播

这样才能把业务状态和链上执行状态拆开管理。

### 关键设计点 2：冻结是为了防止重复占用余额

提现处理中，资金不能继续被别的操作使用。

因此提现申请后通常要做：

*   `available_balance - amount`
*   `frozen_balance + amount`

如果后续失败，再把冻结退回可用。

### 关键设计点 3：拿到 txHash 仍然不能算成功

`txHash` 只能证明：

*   交易已经被构造
*   交易已经尝试广播

但还不能证明：

*   已经被打包
*   执行一定成功
*   确认数已经足够

所以提现最终成功判断，仍然应该以：

*   `receipt.status`
*   `confirmation`

为准。

## 十一、建议的状态流转设计

### 1. 充值状态

第一版可以把充值状态设计为：

*   `PENDING_CONFIRM`
*   `CREDITED`
*   `REORGED`
*   `IGNORED`

含义分别是：

*   `PENDING_CONFIRM`：已识别到候选充值，但确认数不足
*   `CREDITED`：确认数达标，且已完成内部入账
*   `REORGED`：曾识别到，但后续因链上变化失效
*   `IGNORED`：不满足平台识别规则，不进入正式业务

如果后面想做更细，也可以拆出：

*   `DETECTED`
*   `CONFIRMED`
*   `CREDITED`

但第一版建议不要把状态拆得过细。

### 2. 提现状态

第一版可以把提现状态设计为：

*   `PENDING_REVIEW`
*   `REVIEW_REJECTED`
*   `PENDING_BROADCAST`
*   `BROADCASTED`
*   `SUCCESS`
*   `FAILED`

状态含义如下：

*   `PENDING_REVIEW`：已申请，已冻结，待审核
*   `REVIEW_REJECTED`：审核拒绝，冻结退回
*   `PENDING_BROADCAST`：审核通过，等待广播
*   `BROADCASTED`：已广播，等待回执与确认
*   `SUCCESS`：链上成功，冻结正式扣减
*   `FAILED`：链上失败或长时间异常，冻结退回

### 3. 为什么状态机很重要

因为资金系统最怕的不是“逻辑复杂”，而是“状态混乱”。

比如：

*   同一提现单重复广播
*   审核拒绝后还能继续广播
*   成功后还能重复解冻

所以状态机的价值就在于：

*   限定合法流转路径
*   防止重复处理
*   给补偿任务一个明确判断依据

***

## 十二、账本应该怎么设计

账本是这个项目真正的核心。

建议第一版至少有两张核心表：

*   `account_balance`
*   `account_bill`

### 1. `account_balance`

作用：

*   维护用户当前资金状态
*   区分可用余额和冻结余额

建议至少有这些字段：

*   `user_id`
*   `chain`
*   `token_symbol`
*   `available_balance`
*   `frozen_balance`
*   `updated_at`

建议唯一键：

*   `user_id + chain + token_symbol`

### 2. `account_bill`

作用：

*   记录所有资金变动明细
*   支撑审计、排查、对账和补偿

建议至少有这些字段：

*   `user_id`
*   `chain`
*   `token_symbol`
*   `biz_type`
*   `biz_id`
*   `change_amount`
*   `available_after`
*   `frozen_after`
*   `remark`
*   `created_at`

建议唯一键：

*   `biz_type + biz_id`

### 3. 建议的流水类型

第一版至少覆盖：

*   `DEPOSIT_CREDIT`
*   `WITHDRAW_FREEZE`
*   `WITHDRAW_SUCCESS`
*   `WITHDRAW_UNFREEZE`
*   `MANUAL_ADJUST`

### 4. 账本设计最重要的规则

要记住一句话：

`任何余额变化，都必须能在 account_bill 里找到对应流水。`

也就是说，不能只改余额字段，不记流水。

建议唯一键：

*   `request_no`

### 4. `account_balance`

用途：

*   保存余额主状态

### 5. `account_bill`

用途：

*   保存所有资金流水

### 6. 可选支撑表

如果后面开始实现，建议再补两张支撑表：

*   `chain_scan_progress`
*   `task_execution_log`

前者用于记录区块扫描进度，后者用于记录补偿或定时任务执行情况。

这样第一版虽然简单，但已经更像真实后端项目。

## 十四、最关键的 4 个幂等点

### 1. 充值识别幂等

同一条链上 `Transfer event` 不能重复生成多条有效充值记录。

实现抓手：

*   `tx_hash + log_index` 唯一键

### 2. 充值入账幂等

同一笔充值不能重复给用户加余额。

实现抓手：

*   入账前校验充值状态
*   账本流水用 `biz_type + biz_id` 控制唯一性

### 3. 提现申请幂等

同一业务请求不能重复生成提现单。

实现抓手：

*   `request_no` 唯一

### 4. 提现广播幂等

同一提现单不能被重复广播。

实现抓手：

*   状态机限制
*   广播前加锁
*   已存在 `tx_hash` 时禁止再次广播

## 十五、确认数、重查和补偿怎么设计

这是钱包后端特别像资金系统而不是普通 CRUD 的地方。

### 1. 确认数处理

充值和提现都不建议只看“第一次观测结果”。

更稳妥的做法是：

*   充值先待确认，再正式入账
*   提现先广播，再等回执和确认数达标

确认数阈值建议做成配置项，例如：

*   测试环境：较低确认数
*   生产环境：根据链和资产风险调整

### 2. 重查任务

建议至少有两类重查任务：

*   充值确认重查
*   提现回执重查

前者负责推进待确认充值，后者负责处理已广播但未最终落定的提现单。

### 3. 补偿任务

补偿不一定意味着“自动修复一切”，但至少要能做这些事：

*   找出长时间停留在某状态的记录
*   再次查询链上结果
*   如果能确认最终状态，则推进状态机
*   如果不能确认，则打标并等待人工介入

补偿任务的核心价值不是“神奇恢复”，而是避免系统 静默失败。

## 十九、今天最该记住的 8 句话

1.  Day12 的核心不是继续补概念，而是把知识收束成一个项目蓝图。

7.  定时重查、断点续跑和补偿任务，是项目能不能长期稳定运行的关键。
