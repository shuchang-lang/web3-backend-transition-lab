# Day 25 - nonce 锁与串行广播第一版

今天进入 `Day25`。

如果说 `Day20` 解决的是：

`提现广播时怎么预留 nonce，以及广播失败后怎么复用 nonce 重试`

那么 `Day25` 要补的，就是一个更接近真实生产的问题：

`如果同一时间有两轮广播任务一起跑，谁来保证它们不会把同一个热钱包的 nonce 用乱`

这一步非常关键。

因为很多 Web3 提现后端并不是不会发交易，
而是会在并发场景里把交易顺序搞乱。

而一旦 `nonce（交易序号）` 被并发任务用坏，
后续就很容易出现：

- 两笔交易抢同一个 nonce
- 后发任务把先发任务顶掉
- 本地状态和链上顺序不一致
- 排障时很难解释到底是哪一轮任务抢占了广播机会

Day25 第一版做的，就是先把这类风险在当前单实例学习项目里关住。

---

## 一、为什么 Day25 是提现执行系统里最有 Web3 味道的一步

对于传统 Java 后端来说，你可能已经很熟悉：

- 分布式锁
- 任务串行化
- 防重复执行
- 下游幂等

但在 Web3 提现系统里，`nonce` 让这个问题变得更具体。

因为 EVM 链上的同一个出金地址，发出的交易天然带有：

- 单地址递增顺序

也就是说，一个热钱包地址的链上交易不是普通“随便并发发就行”的请求，
而是带有明确顺序约束的。

如果系统同时起了两轮提现广播任务，它们都去做下面这些事：

1. 查询当前建议 `nonce`
2. 扫描本地待广播订单
3. 给订单预留 `nonce`
4. 立即广播

那并发风险就会很高。

Day25 的核心目的，就是先回答这个问题：

`同一实例内，怎么保证同一时间只允许一轮提现广播任务推进 nonce 分配和广播`

---

## 二、Day25 第一版的边界是什么

`nonce` 并发控制如果做深，也会非常大。

你完全可以继续扩展：

- 多实例数据库锁
- Redis 分布式锁
- 热钱包维度分片锁
- 广播队列中心
- 按链 / 按钱包顺序分桶

但 Day25 第一版我先只做最小闭环。

### 1. 先只解决单 JVM 并发问题

当前项目还是一个单实例学习工程，
所以 Day25 第一版先采用：

- `local lock（本地锁）`

也就是：

`同一 JVM 内，同一时间只允许一轮提现广播任务真正执行`

这不是最终形态，
但它非常适合作为第一版。

因为你先要把：

- 并发风险是什么
- 任务串行化边界在哪里
- 广播入口怎么保护

这些核心工程判断补清楚。

### 2. 串行保护放在任务入口层

Day25 第一版没有把锁散落在：

- `nonce` 查询方法里
- `reserveNonce(...)` 里
- 单笔广播逻辑里

而是放在：

- `WithdrawExecutionTask.runBroadcastOnce()`

这个任务入口层。

这样做的好处很明显：

1. 能明确表达“整轮广播任务是否允许开始”
2. 一旦拿到锁，整个批次就天然串行
3. 业务层 `WithdrawExecutionAppService.broadcastPendingOrders()` 还能继续保持清晰

这和很多 Java 后端里的：

- Job 级别锁
- 任务互斥
- 批处理串行入口

是同一种思路。

### 3. 当前仍按订单 ID 顺序逐笔广播

Day25 没有额外引入新的优先级队列，
而是沿用原本就已经存在的：

- `orderByAsc(id)`

这意味着当前批次内的订单处理顺序仍然清晰可解释：

`按订单创建顺序逐笔预留 nonce、逐笔广播`

也就是说，Day25 第一版做的是：

- 先把“并发抢 nonce”的问题关掉
- 暂时不把“复杂队列调度”一起做大

这个边界很合理。

## 三、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经补了下面几块核心能力。

### 1. 新增本地串行锁 `WithdrawBroadcastLock`

新增：

- `WithdrawBroadcastLock`

它内部使用的是：

- `ReentrantLock(true)`

也就是公平锁。

为什么这里选公平锁？

因为在任务串行化场景下，
公平锁至少能让后来的广播任务按更可预测的顺序排队竞争，
减少“某一轮一直拿不到机会”的偶发性。

虽然当前学习项目不一定会真正压测出这个差异，
但这个选择本身很符合：

`资金执行任务更偏保守、更偏可解释`

的设计风格。

### 2. 广播任务入口增加串行保护

`WithdrawExecutionTask.runBroadcastOnce()` 现在会先做三层判断：

1. 当前环境是否具备可广播条件
2. 当前是否已经有另一轮广播任务在执行
3. 如果拿到锁，再真正开始广播批次

也就是说，Day25 之后，广播任务入口的语义已经变成：

`先判断能不能广播，再判断允不允许这一轮广播开始`

这一步非常重要。

因为它意味着当前系统第一次开始明确区分：

- “能力不足所以不能执行”
- “环境可执行，但当前为了保护 nonce 不允许并发执行”

### 3. 新增“锁占用时跳过”的明确返回语义

当前如果广播锁没有拿到，
任务不会继续推进，也不会假装执行成功，
而是会直接返回：

- `executed = false`
- 并附带说明：
  - `当前已有另一轮提现广播任务在执行中，已跳过本轮请求`

这比“静默失败”或者“返回 0 条处理但不解释原因”要专业很多。

因为当前系统已经开始表达：

`不是没有订单，而是为了保护热钱包 nonce，主动跳过了这一轮并发请求`

### 4. `WithdrawTaskRunResponse` 增加任务执行语义

`WithdrawTaskRunResponse` 新增了：

- `executed`
- `remark`

这一步看似只是响应对象多了两个字段，
但它其实解决了一个很真实的表达问题：

`processedCount = 0` 到底是因为没有数据，还是因为任务被跳过了？

Day25 之后，这个问题终于可以被清楚地区分开了。

这对后台运维、接口展示、面试表达都很有帮助。

### 5. 广播任务现在会区分三类结果

`runBroadcastOnce()` 当前至少能表达三类典型结果：

1. 配置不完整，跳过广播
2. 另一轮任务正在执行，跳过广播
3. 成功拿到锁，串行完成一轮广播

如果本轮拿到锁但没有待广播订单，
也会明确返回“当前没有待广播的提现订单”。

也就是说，Day25 开始，广播任务已经不像以前那样只是一个“黑盒触发器”，
而是逐步有了：

`可解释的任务运行结果`

### 6. 广播服务层补充顺序语义注释

`WithdrawExecutionAppService.broadcastPendingOrders()` 现在也明确强调：

- Day25 第一版在任务入口层先拿串行锁
- 当前批次继续按订单 ID 升序逐笔处理
- 这样 nonce 预留和广播顺序保持稳定、可解释

虽然这一步不改变业务逻辑，
但它把 Day25 的设计意图补得更清楚了：

`串行保护 + 顺序处理`

是一起配合的，而不是只做了一个锁就算结束。

### 7. 测试也同步补到了 Day25 语义

当前测试已经新增并覆盖：

1. 当另一轮广播任务已经在执行中时，本轮会跳过
2. 当成功拿到锁时，本轮会执行广播并在结束后释放锁
3. 当拿到锁但没有待广播订单时，也会正常释放锁

到这里为止，当前项目测试总数已经推进到：

`49`

这说明 Day25 不是“只在文档里说用了锁”，
而是把锁分支和释放语义真正做成了可验证行为。

## 四、Day25 最值得记住的几个工程判断

### 1. `nonce` 问题本质上是顺序竞争问题

很多人第一次接触 Web3 后端时，会把 `nonce` 只理解成一个“链上自增数字”。

但对提现系统来说，它更像是：

`热钱包交易执行顺序的唯一编号`

一旦多个任务同时竞争这个编号，
整个执行链路就会变得不可控。

所以 Day25 的本质不是“多加一个锁”，
而是：

`开始把热钱包顺序约束当成系统级问题处理`

### 2. 第一步先做任务级串行化，比先做复杂分布式锁更稳

Day25 第一版没有一上来就做很重的：

- 分布式锁
- 跨实例协调
- 锁租约续期

而是先做：

- 单 JVM 任务级串行化

这其实很符合真实工程推进方式。

因为你需要先确认：

1. 锁应该放在哪一层
2. 拿不到锁时接口怎么返回
3. 整轮任务的执行边界是什么

这些问题比“锁用哪种中间件”更基础也更重要。

### 3. 跳过执行也必须可解释

这是 Day25 非常适合拿去面试讲的一点。

如果一轮广播任务因为锁被占用而没有执行，
系统必须能够明确表达：

`我没有执行，不是因为没订单，而是因为当前为了保护 nonce 主动放弃并发执行`

这类“主动跳过”的可解释性，
其实是成熟任务系统很重要的特征。

### 4. 锁保护的是“批次进入权”，不是单笔交易本身

Day25 当前锁放在任务入口，而不是某个单笔广播方法里。

这说明当前设计保护的核心是：

`哪一轮批次有资格开始预留 nonce 和执行广播`

这比只在单笔方法上加锁更清晰，
也更适合后面继续做：

- 广播队列
- 钱包分桶
- 分实例任务分配

### 5. Day25 第一版是有意保留升级空间的

当前 `WithdrawBroadcastLock` 的注释已经明确说明：

`如果后续要支持多实例部署，再升级成数据库锁或分布式锁`

这点很重要。

因为好的第一版，不是 pretending 自己已经是最终版，
而是要能清楚地告诉别人：

`我先解决了当前项目最真实的问题，同时保留了下一阶段扩展方向`

## 五、Day25 之后，提现广播链路发生了什么变化

到 Day25 为止，提现广播这段链路已经从原来的：

`扫描待广播订单 -> 预留 nonce -> 广播`

扩展成：

1. 手动触发广播任务
2. 检查环境是否具备广播条件
3. 先尝试获取本地串行广播锁
4. 如果锁已被占用，则直接跳过
5. 拿到锁后，按订单 ID 升序扫描待广播订单
6. 逐笔预留或复用 `nonce`
7. 逐笔发起链上广播
8. 批次结束后释放锁

也就是说，当前系统已经第一次具备了：

`在同一实例内，保护热钱包 nonce 不被并发广播任务抢乱`

的能力。

这一步虽然还不是完整生产版，
但已经非常接近很多真实资金后端的第一阶段治理思路。

## 六、当前版本还没有做什么

虽然 Day25 已经补了本地串行广播保护，但它依然只是第一版。

当前还没有做：

1. 多实例数据库锁或分布式锁
2. 按热钱包 / 按链 / 按币种维度的细粒度锁
3. 更复杂的广播队列和优先级调度
4. 更完整的锁竞争监控和告警
5. `nonce` 堵塞检测与链上替换交易策略

所以目前最准确的表达应该是：

`我已经实现了提现广播阶段的单 JVM nonce 串行保护第一版，系统能在同一实例内避免并发广播任务竞争热钱包 nonce，并明确表达锁占用导致的跳过结果，但还没有进入多实例分布式锁阶段`

这个表述会比“我已经彻底解决了 nonce 并发问题”更真实、更专业。

## 七、从 GitHub 展示和面试角度，Day25 的价值是什么

Day25 的价值非常高，因为它开始明显进入：

`Web3 资金后端特有的执行稳定性问题`

这一天最能体现的几个能力是：

### 1. 你知道同一热钱包的广播不是普通并发任务

这本身就是一个很强的 Web3 后端判断。

### 2. 你会把链上顺序约束翻译成后端治理动作

不是停留在“nonce 需要递增”的概念层面，
而是把它真正落成：

- 串行锁
- 任务互斥
- 可解释的跳过结果

### 3. 你会用保守但真实的方式推进第一版

先做单 JVM 保护，再预留升级到数据库锁 / 分布式锁的空间，
这是一种很成熟的工程节奏。

对 `钱包后端 / 交易所后端` 面试来说，这种表达会很加分。

这样项目会继续从“单点能力越来越强”，推进到：

`整套任务系统开始更像真实后端`

## 阶段结论

Day25 的本质，不只是多了一个本地锁类，也不只是广播任务多了一层 tryLock。

它真正补上的，是：

`系统开始把热钱包 nonce 顺序约束，显式建模成任务级串行执行问题`

更准确地说，到今天为止，这个项目主线已经形成了：

`充值扫描 -> 确认入账 -> reorg 风险识别 -> 充值补偿 -> 提现申请 -> 冻结 -> 审核 -> 广播 -> 回执同步 -> 超时巡检 -> nonce 串行保护`

这条主线已经明显不再只是“能跑通流程的 demo”，
而是在一步一步长成一个：

- 理解链上异常
- 理解账务补偿
- 理解任务治理
- 理解热钱包执行稳定性

的钱包后端学习工程。
