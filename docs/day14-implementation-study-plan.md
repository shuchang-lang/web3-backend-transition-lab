## 二、为什么 Day14 不能直接跳去做复杂充值监听

很多人到这一步会想：

`既然骨架有了，是不是下一步就直接全力做 ERC-20 监听？`

方向没错，但顺序还需要更稳一点。

因为一个像样的充值监听，不只是“从链上拿日志”这么简单，它至少还依赖这些前置条件：

- 地址管理得稳定
- 余额主表存在
- `deposit_record` 建模清楚
- 扫描进度怎么保存想清楚
- 确认数推进路径明确
- 正式入账怎么和账本写入绑定清楚

所以 Day14 更合理的目标，不是“一口气把充值做完”，而是：

`把地址管理和余额查询从骨架推进成稳定基座，并为充值记录和扫描进度铺路。`

---

## 三、Day14 的核心主题是什么

建议把 Day14 的主题定义成：

`把“骨架工程”推进成“具备充值监听前置条件的最小后端底座”。`

这一天最应该关注的，不是写多少代码，而是把下面几件事真正做实：

1. 地址管理再收紧一点
2. 余额查询再完整一点
3. 充值记录模型开始进入代码层
4. 区块扫描进度开始进入代码层
5. 为后续 ERC-20 日志消费准备好入口

## 四、Day14 最值得做的 5 件事

### 1. 把地址管理模块做得更像真实后端

Day13 里地址管理已经能跑通，但它还是“骨架版”。

Day14 建议继续补这些点：

- 地址状态枚举化，而不是只用字符串
- 地址唯一性规则再收紧
- 地址分配接口的返回结构更稳定
- 可以补一个地址列表查询或按资产维度查询

为什么先做这个：

因为后面充值监听判断归属时，本质上就是在查地址表。

### 2. 把余额查询做成更稳定的账本入口

现在的余额查询已经能返回：

- `available_balance`
- `frozen_balance`

Day14 可以继续补：

- 返回结构更统一
- 链和币种维度更明确
- 空数据场景的处理更清楚
- 为后面账本流水预留字段口径

为什么先做这个：

因为后面无论充值成功还是提现冻结，最终都要落到余额模型。

### 3. 把 `deposit_record` 真正接进代码

这是 Day14 最关键的“向充值监听迈一步”动作。

建议至少先做：

- `deposit_record` 实体
- Mapper
- 基础状态定义
- 唯一键语义

哪怕这一天还不真正扫链，也应该先把“候选充值记录怎么落库”想清楚并进代码。

### 4. 增加区块扫描进度模型

哪怕第一版还没开始真正扫区块，也建议把下面这个概念先落下去：

- `chain_scan_progress`

至少明确：

- 扫的是哪条链
- 扫描任务名是什么
- 扫到哪个区块
- 最近一次更新时间

为什么现在就要做：

因为充值监听真正像后端工程，而不是 demo 的关键点之一，就是 `断点续跑`。

### 5. 预留充值监听任务入口

Day14 不一定要完整实现监听逻辑，但建议至少预留：

- `deposit scan task`
- `deposit service`
- `deposit parser`

哪怕先是空实现，也要把后续代码该落在哪一层想清楚。

## 五、Day14 的学习重点不只是“会写代码”，而是会做工程判断

这一天真正值得训练的，是下面这些判断能力：

### 1. 哪些对象应该先实体化

先实体化什么，代表你对系统核心对象的判断。

Day14 最值得优先实体化的通常是：

- `wallet_address`
- `account_balance`
- `deposit_record`
- `chain_scan_progress`

### 2. 哪些能力先做最小版

不要一开始就做：

- 完整充值监听闭环
- 完整确认数推进
- 多链抽象
- 完整账本流水系统

先把最小版做出来，后面再一层层补。

### 3. 哪些边界必须先留好

Day14 虽然功能不算多，但边界必须开始明确：

- Controller 只接请求
- Application Service 负责业务编排
- Mapper 只处理持久化
- Web3 调用不要直接写进 Controller
- 监听任务和接口层不要混在一起

这一步对后面非常重要。

## 八、后面几天最容易犯的 5 个错误

### 1. 一开始就想做太全

比如：

- 多链
- 多币种
- 归集
- MPC
- 风控系统

这些都不是当前阶段重点。

### 2. 还没把数据模型立稳，就急着写复杂监听

这样后面会不断返工。

### 3. 把链交互逻辑直接写进业务层

这样代码很快会变乱，后面也难以替换节点或 mock。

### 4. 忽略确认数和状态流转

这会让充值链路看起来“能跑”，但实际上没有工程价值。

### 5. 忽略 GitHub 展示节奏

实现阶段不只是写代码，还要同步想：

- README 怎么更新
- 哪些点能展示
- 哪些能力能讲成项目亮点
