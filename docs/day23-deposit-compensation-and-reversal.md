# Day 23 - 充值补偿与冲正第一版

今天进入 `Day23`。

如果说 `Day22` 解决的是：

`怎么识别哪条充值记录疑似因为 reorg（链重组）而失效`

那么 `Day23` 要补的，就是更贴近资金后端本质的下一步：

`识别出异常以后，账要怎么动`

这一步非常关键。

因为对钱包后端、交易所资金后端来说，很多系统并不是不会“发现异常”，
而是不会把异常落成：

- 可执行的补偿动作
- 可审计的账务流水
- 可追踪的终态状态机

Day23 第一版做的，就是这三件事里的最小闭环。

---

## 一、为什么 Day23 要紧接 Day22

Day22 做完以后，系统已经可以把历史充值记录标记成：

- `REORG_SUSPECTED`

这说明系统已经第一次承认一个现实：

`昨天已经入账的充值，今天可能不再可靠`

但如果系统只是把状态标记出来，不继续处理资金，
那余额主表、账务流水、业务状态之间就会长期停留在一个“知道有问题、但钱没动”的中间态。

这个中间态在真实项目里当然会存在，
但它不能永远没人处理。

所以 Day23 的目标不是把问题做复杂，
而是先把最小动作补起来：

1. 找到真正需要冲正的异常充值
2. 执行一次最小的账务扣回
3. 把充值记录推进到新的终态
4. 让后续对账可以解释这次补偿动作

从 Java 后端视角看，这一步很像你熟悉的：

- 失败补偿
- 状态推进
- 账务审计
- 风险敞口显式化

只不过这里的问题来源不再是 MQ 重复消费或第三方回调延迟，
而是：

`链上历史结果本身可能变化`

---

## 二、Day23 第一版的边界是什么

充值补偿如果往深了做，会非常大。

比如你完全可以继续扩展：

- 补偿审批流
- 人工复核流
- 风险台账
- 冲正原因落库
- 二次补偿幂等键
- 自动冻结账户
- 风险通知与告警

但 Day23 第一版我故意只做最小闭环。

### 1. 只处理已经正式入账、后来被标记异常的充值

当前只处理：

- `status = REORG_SUSPECTED`
- 且 `creditedAt != null`

为什么要同时判断这两个条件？

因为这代表：

`这条充值之前确实已经给用户加过钱`

如果一条记录只是候选充值、或者还在待确认阶段，
那它就还没有真正进入资金账本，不应该走“冲正已入账资金”的逻辑。

### 2. 不新增复杂补偿元数据

Day23 第一版不新增表字段，不做独立补偿表，
先不沉淀诸如：

- 补偿批次号
- 补偿发起人
- 风险等级
- 原因分类
- 审批状态

这样做的目的不是偷懒，
而是先确认最小补偿链路本身能跑通。

### 3. 最小补偿动作只有四步

当前版本对每一条异常充值只做四件事：

1. 从 `account_balance.available_balance` 扣回原充值金额
2. 允许 `available_balance` 变成负数
3. 插入一条新的账务流水 `DEPOSIT_REORG_DEDUCT`
4. 把充值记录推进到 `REORG_COMPENSATED`

这个设计非常像真实资金系统里的“先表达事实，再继续治理”。

也就是说，Day23 第一版不追求立刻把所有风险都消灭，
而是先把它准确地写进系统状态里。

---

## 三、为什么允许可用余额变成负数

这应该是 Day23 最值得理解的一个工程判断。

对很多传统业务系统来说，看到余额变负，第一反应会是：

`这是不是出 bug 了`

但在资金补偿场景里，负数不一定是 bug，
它也可能是系统在诚实地表达：

`这笔原本已经给用户入账的钱，后来被确认无效，但用户可能已经把这部分钱花掉了`

比如：

1. 用户收到一笔充值
2. 系统达到确认数后正式入账
3. 用户又基于这笔钱发起提现或后续资金动作
4. 后来这笔充值被识别成 `REORG_SUSPECTED`
5. 系统需要把原来的入账金额扣回

这时如果余额已经不够，最真实的表达就不是“禁止扣回”，
而是：

`允许余额变负，把风险敞口显式暴露出来`

从账务角度看，这比“为了不让数字难看就不扣回”要专业得多。

因为 Day23 的目标不是粉饰余额，
而是把系统当前真实处境表达清楚：

- 这笔资金原本已记入用户资产
- 后来被识别成无效
- 现在平台对该用户形成待追偿风险敞口

这和 Java 后端里常见的：

- 欠费状态
- 待补扣状态
- 保证金不足

本质上是同一类建模思想。

## 四、今天代码里实际补了什么

当前 `practice/web3-wallet-backend-demo` 已经补了下面几块核心能力。

### 1. 充值状态新增 `REORG_COMPENSATED`

`DepositStatusConstants` 新增：

- `REORG_COMPENSATED`

并且 `DepositRecord` 增加了：

- `markReorgCompensated()`

这一步很关键。

因为一旦系统已经完成冲正，就应该把这条风险记录推进到新的终态，
避免后续任务再次重复处理同一条记录。

从状态机视角看，Day23 之后充值记录的语义已经从：

- `PENDING_CONFIRM`
- `CREDITED`
- `REORG_SUSPECTED`

继续扩展成：

- `REORG_COMPENSATED`

也就是说，它不再只是“发现风险”，而是已经能表达：

`风险已经被执行过一次最小补偿动作`

### 2. 账务流水新增 `DEPOSIT_REORG_DEDUCT`

`AccountBillBizTypeConstants` 新增：

- `DEPOSIT_REORG_DEDUCT`

`AccountBill` 新增工厂方法：

- `createDepositReorgDeduct(...)`

这一步是 Day23 的核心之一。

因为资金系统最怕的一件事就是：

`余额变了，但不知道为什么变`

如果只是把余额主表减掉金额，却不写流水，
那后续你做：

- 对账
- 排查
- 审计
- 面试讲解

都会很被动。

新增补偿流水以后，系统就能明确解释：

`这次余额扣减不是提现、不是人工改数，而是链重组风险冲正`

这就是典型的账务可审计设计。

### 3. 余额实体新增 `deductAvailable(...)`

`AccountBalance` 新增：

- `deductAvailable(BigDecimal amount)`

而且注释里明确说明：

`Day23 第一版允许可用余额出现负数`

这一步把“金额扣减的业务语义”收敛到了实体内部，
避免应用层直接到处散落 `availableBalance.subtract(...)`。

对于后面继续扩展冻结、追偿、补扣策略，会更稳。

### 4. 新增补偿任务 `DepositCompensationTask`

新增：

- `DepositCompensationTask`

当前逻辑非常清晰：

1. 查出所有 `REORG_SUSPECTED` 且 `creditedAt != null` 的充值记录
2. 查询对应用户资产余额主表
3. 如果余额主表不存在，就先创建一条零余额记录
4. 从可用余额扣减原充值金额
5. 插入 `DEPOSIT_REORG_DEDUCT` 流水
6. 把充值记录推进到 `REORG_COMPENSATED`
7. 返回本轮补偿结果

这个任务把 Day22 的“风险识别”真正推进成了 Day23 的“账务处理”。

### 5. 新增后台接口

`AdminTaskController` 新增：

- `POST /admin/deposit/compensate/run`

这意味着当前系统已经具备一个很像真实后台运维工具的能力：

`先做风险巡检，再按批次手动执行一轮补偿`

这比“一上来就偷偷自动改余额”更适合作为学习项目的第一版，
也更符合很多真实团队先保守上线的节奏。

### 6. 对账口径同步纳入补偿流水

`AccountReconcileAppService` 里，
`resolveBillAssetDelta(...)` 已经把：

- `DEPOSIT_REORG_DEDUCT`

纳入“总资产变化流水”的口径。

这一步非常重要。

因为 Day23 之后，账务总资产的变化不再只有：

- `DEPOSIT_CREDIT`
- `WITHDRAW_DEDUCT`

还包括：

- `DEPOSIT_REORG_DEDUCT`

如果不把它纳入对账口径，
那系统虽然补了冲正动作，但对账会继续把它当成“莫名其妙少了一笔钱”。

### 7. 测试同步补到了 Day23 语义

当前测试已经新增并覆盖：

1. 没有可补偿记录时，任务会返回 no-op
2. 正常冲正已入账异常充值时：
   - 余额被扣减
   - 插入 `DEPOSIT_REORG_DEDUCT`
   - 充值状态推进到 `REORG_COMPENSATED`
3. 余额主表不存在时，也会先补零余额记录并允许扣成负数
4. 控制器可以正常触发 `POST /admin/deposit/compensate/run`
5. 对账逻辑会把 `DEPOSIT_REORG_DEDUCT` 纳入资产口径

到这里为止，当前项目测试总数已经推进到：

`39`

这说明 Day23 不是“只在 README 里说做了补偿”，
而是代码、测试、文档都完成了同步。

## 五、Day23 之后，充值主链路发生了什么变化

到 Day23 为止，充值链路已经从最初的：

`扫日志 -> 候选充值 -> 确认数推进 -> 正式入账`

继续扩展成：

1. 扫描 ERC-20 `Transfer event`
2. 识别候选充值
3. 刷新确认数
4. 达到阈值后正式入账
5. 后台巡检历史充值是否疑似 `reorg`
6. 命中异常则标记 `REORG_SUSPECTED`
7. 后台触发补偿任务
8. 扣回可用余额
9. 写入 `DEPOSIT_REORG_DEDUCT`
10. 把充值推进到 `REORG_COMPENSATED`

也就是说，项目已经第一次具备了：

`发现链上历史异常 -> 执行最小账务冲正`

的闭环。

这一步对钱包后端、交易所后端都非常重要，
因为它意味着这个系统已经开始理解：

`链上主链路不是结束在“入账成功”，而是结束在“入账结果仍然成立”`

## 六、Day23 最值得记住的几个工程判断

### 1. 风险识别和资金冲正依然要拆阶段

Day22 和 Day23 连在一起看，会发现这里一直在坚持一个原则：

1. 先识别风险
2. 再执行补偿

这比“巡检任务一发现异常就直接改账”更稳，
也更方便后面扩展：

- 人工审批
- 白名单放行
- 分级补偿

### 2. 冲正不是删记录，而是新增可解释动作

Day23 没有去“抹掉之前那条充值”，
也没有去“回写覆盖历史流水”，
而是新增一条：

- `DEPOSIT_REORG_DEDUCT`

这就是很典型的账务设计思路：

`历史动作保留，再追加新的冲正动作`

这样系统才能保留完整时间线。

### 3. 负余额是风险敞口，不是展示 bug

这一步非常适合拿去面试里讲。

因为它体现了你已经不再把余额当成“只能好看不能难看”的前端展示数字，
而是把它当成：

`资金事实`

当事实就是“平台已经先把钱给了用户，现在链上结果回滚了”，
那系统就应该有能力表达负债和敞口。

### 4. 补偿之后必须进入终态

如果一条充值已经冲正完成，
却仍然停留在 `REORG_SUSPECTED`，
后续任务就很容易重复扣减。

所以 `REORG_COMPENSATED` 这个状态看起来只是多了一个常量，
但它本质上是在解决：

`补偿任务的重复执行风险`

### 5. 对账口径一定要跟着状态机一起演进

很多系统会在 Day23 这种阶段犯一个典型错误：

功能做完了，但对账口径没跟上。

结果就是：

- 余额改了
- 流水也写了
- 但对账依然解释不通

当前项目把 `DEPOSIT_REORG_DEDUCT` 纳入 `billAssetDeltaAmount`，
就是在补这个口径一致性。

## 七、当前版本还没有做什么

虽然 Day23 已经完成最小补偿闭环，但它依然只是第一版。

当前还没有做：

1. 自动定时触发补偿任务
2. 补偿审批流和人工复核台账
3. 独立补偿记录表或补偿批次号
4. 更细粒度的幂等控制和冲正原因分类
5. 补偿告警、审计报表、风险订阅
6. 链上重查后自动恢复或更复杂的补偿策略

所以目前最准确的表达应该是：

`我已经实现了异常充值的最小补偿与冲正第一版，系统能扣回已入账金额、写补偿流水、推进终态，但还没有进入完整的自动治理和审批体系`

这个表达比“我已经彻底解决了链重组补偿”更真实，也更专业。

## 八、从 GitHub 展示和面试角度，Day23 的价值是什么

Day23 的价值非常高，因为它开始把这个仓库从“会扫链、会入账”的项目，
继续往“懂资金异常治理”的方向推进。

这一天最能体现的几个能力是：

### 1. 你不只是会 happy path

你已经开始处理：

- 已入账后失效
- 风险补偿
- 账务冲正
- 负债敞口

这比单纯实现充值、提现主链路更有后端含量。

### 2. 你会用状态机表达资金治理过程

从 `REORG_SUSPECTED` 到 `REORG_COMPENSATED`，
这其实就是在表达：

`发现问题 -> 执行动作 -> 进入终态`

这非常贴近真实后端系统的治理思路。

### 3. 你会把补偿动作落到账本里

这件事很重要。

因为钱包后端、交易所后端最核心的不是“接口写了几个”，
而是：

`系统能不能把每一笔资金变化解释清楚`

Day23 正在补这件事。

## 九、Day24 最合理的推进方向是什么

Day23 做完以后，最自然的下一步不再是继续深挖充值，
而是去补提现链路里的另一类真实异常：

`提现回执超时巡检与异常订单治理第一版`

因为当前提现链路虽然已经有：

- 广播
- nonce 预留
- 失败重试
- 回执同步

但还缺一类很真实的治理问题：

`订单已经 BROADCAST_SUBMITTED 很久了，却迟迟没有最终结果，接下来怎么办`

所以 Day24 很适合继续补：

1. 长时间未完结提现订单巡检
2. 重新查回执
3. 区分继续等待、可重试、待人工处理

这样项目会从“充值异常补偿”继续延伸到“提现尾部异常治理”，
工程完整度会再上一个台阶。

---

## 阶段结论

Day23 的本质，不只是多了一个任务接口，也不只是多了一条流水类型。

它真正补上的，是：

`系统已经能把“发现异常充值”推进成“执行最小账务冲正”`

更准确地说，到今天为止，这个项目主线已经形成了：

`充值扫描 -> 候选识别 -> 确认入账 -> 提现申请 -> 冻结 -> 审核 -> nonce 预留 -> 广播 -> 回执跟踪 -> 手动补扫 -> 资产对账 -> reorg 风险识别 -> 异常充值补偿`

这条主线已经越来越不像“演示型 demo”，
而越来越像一个开始理解：

- 链上异常
- 账务补偿
- 状态终态
- 风险敞口

的钱包后端学习工程。
